# B1 向量化能到多少 ms/step（含 bit-exact 约束）

> PATH: DENSE。实测者：bench-builder。回应 Lead 的问题：
> 「敢不敢把 B1（全 k0=20，含 20% 标量尾块）也向量化，实测它到底能到多少 ms/step」。
> 探针：`train/src/bench_b1_vec.rs`（bin `vmlm-b1-vec`）。

---

## 0. 一句话结论

| 版本 | ms/step | vs S0 | bit-exact? |
|---|---|---|---|
| **S0 标量现状**（`b1_pure.rs:74` 逐字复刻） | **559~571** | 1.00x | 基准 |
| **S1 向量 gather + 标量顺序累加** | **273~278** | **2.04~2.08x** | ✅ **是（0/1536）** |
| S2 向量 gather + SIMD 8 路归约 | 166~312（不稳） | 1.8~3.4x | ❌ 否（841/1536 分叉） |
| S3 无 gather 天花板 | **117** | 4.87x | — |

⇒ **B1 向量化（且保住 bit-exact）实测可到 ~275 ms/step，2.05x，不是 7x。**
⇒ 天花板（去掉 gather）只有 **117 ms/step**，即 B1 的极限是 4.87x，**到不了 76.8x**。
⇒ 与 76.8x 对应的 98.7（或修正后的 11.2）ms/step **即使完全不 gather 也够不着**。

**关键：Lead 猜测的「~7x 空间」不成立。** 原因见 §3 —— 那是把
「向量化 gather 的乘积」误当成「向量化整个 B1」；实测 S1 只拿到 2.05x，
因为「取乘积」在 S0 里只占一部分，且 bit-exact 契约禁止 8 路归约（§1）。

---

## 1. 为什么必须先说 bit-exact 约束

`core/src/b1_pure.rs` 头部把**累加顺序写成了契约**，不是风格问题：

> * 行内按 j 升序（`0..k0`）；
> * **单个标量累加器 acc —— 不做 8 路 SIMD 归约（归约会改变分组，进而改变位型）**；
> * **首个命中直接赋值 `acc = term`**，而不是从 `0.0f32` 起加
>   （因为 `0.0 + (-0.0) = +0.0`，位型不同）。

B1 的验收判据 **A1 是 `f32::to_bits()` 逐位比较**。所以「向量化 B1」有一个硬约束：
**不能改累加分组**。因此本探针测三版，并把 bit-diff **一起**报出：

- **S1 是唯一既能加速又保住 A1 的路线** —— 它的数字才是「B1 能到多少」。
- S2 用来量化「若允许放弃 bit-exact 能多拿多少」—— 这是**决策输入，不是实现建议**。

实测的 A1 判据（d=1536，3 次运行完全一致）：
```
S1 bit-different = 0      / 1536   max|diff|=0.000e0    <= PASS (bit-exact)
S2 bit-different = 841    / 1536   max|diff|=5.960e-8   <= FAIL (归约改变分组)
```
⇒ **确认 b1_pure.rs 头部那条警告是真的**：8 路归约让 841/1536 个输出的位型分叉。
这条不是理论风险，是实测。

## 2. 原始输出（d=1536, k0=20, reps=400，3 次独立进程）

```
  S0 标量现状 (b1_pure.rs:74 逐字复刻)     0.03640 / 0.03700 / 0.03720 ms   1.185~1.211 ns/conn
  S1 向量gather + 标量顺序累加 [bit-exact] 0.01780 / 0.01810 / 0.01790 ms   0.579~0.589 ns/conn
  S2 向量gather + SIMD归约 [会分叉]        0.01080 / 0.02030 / 0.01080 ms   0.352~0.661 ns/conn
  S3 无gather 天花板                       0.00770 / 0.00760 / 0.00760 ms   0.247~0.251 ns/conn
```

外推到 5 matvec × 24 层 × 128 位置（×15360，与 Lead 的 `lead_b1_gap.rs` 同一乘数）：

| 运行 | S0 | S1 | S2 | S3 |
|---|---|---|---|---|
| #1 | 568.3 | **278.0** | 311.8 | 116.7 |
| #2 | 571.4 | **274.9** | 165.9 | 116.7 |
| #3 | 568.3 | **274.9** | 165.9 | 116.7 |

**校准**：S0 = 559~571 ms/step 与 Lead 独立测的 **566.8**（`lead_b1_gap.rs` L1）吻合 ✓
**天花板互校**：S3 = 116.7~118.3 与 Lead 的 **L4 = 122.9** 吻合 ✓

**两处不确定度（如实报告）**：
- **S1 稳定**：2.04 / 2.08 / 2.07x，ns/conn 0.579~0.589（±1%）。
- **S2 不稳定**：1.82x~3.44x，ns/conn 0.352~0.661（**近 2 倍摆动**）。
  S2 的值不可精确引用；它的用途只是说明「放弃 bit-exact 能到 ~166 ms/step 量级」。
  摆动原因未查清（推测与 gather 与归约的端口争用/对齐有关），**不下结论**。

## 3. 为什么是 2.05x 而不是 7x（Lead 猜错了，原因值得记）

Lead 的推理是：「我的 L1 = 1.19 ns/conn，你的 V1 = 0.167 ns/conn ⇒ 有 ~7x 空间」。

**这个比较跨了两个不同的东西**：
- `lead_b1_gap.rs` 的 **L1/L2** 与我的 **V1/V2** 测的是**「取乘积」这一步**
  （强度行：`gather + mul + abs`），**不含累加**。
- `b1_forward` 的完整工作量是**「取乘积 + 按序累加」**。

S1 把「取乘积」向量化了（这部分确实快），但**累加仍是标量串行单累加器**
（bit-exact 要求，见 §1）⇒ **瓶颈转移到累加依赖链上**。

证据（全部实测，ns/conn）：
```
S0 = 1.204  （取值标量 + 累加标量）
S1 = 0.583  （取值向量 + 累加标量）  -> 省掉的是"取值"那部分
S3 = 0.247  （取值连续 + 累加标量）  <- 天花板：连取值都免费了
```
⇒ S1 之后仍有 **S1−S3 = 0.583−0.247 = 0.336 ns/conn** 是 gather 成本。

**S3 = 0.247 ns/conn 说明什么（以及我第一版说错了什么）**：
我第一版写「0.247 ns/conn ≈ 0.74 周期/连接，即 f32 add 的 4 周期延迟链」——
**这是错的，自相矛盾**：0.74 周期 **小于** 4 周期，不可能是「4 周期延迟链」。
按 3~3.5 GHz 折算，S3 是 **0.74~0.86 周期/连接**。

⇒ 正确的解释：**S3 不是延迟受限，而是吞吐/带宽受限**。
它在 0.74~0.86 周期/连接上跑完，说明**多个加法链在重叠**
（`while` 循环里每次迭代独立，只有循环内的 `acc` 依赖是串行的，
而内层 j 循环 20 次迭代中的乘加可以流水起来）。
⇒ 所以「累加依赖链是 B1 的天花板」这个说法**我没有证据**，撤回。

**能确定的**（全部实测，不推断微架构）：
```
S0 = 1.204  取值标量 + 累加标量
S1 = 0.583  取值向量 + 累加标量   -> 向量化"取值"贡献 0.621 ns/conn
S3 = 0.247  取值连续 + 累加标量   -> 再省 0.336 ns/conn (gather 成本)
```
⇒ **S1→S3 之间那 0.336 ns/conn 是 gather 的成本**，这部分转译器改不了。
⇒ **S3 到 0 之间那 0.247 ns/conn 是「取值+累加」的实测下限**，
   其微架构成因（延迟 or 吞吐 or 带宽）**本探针无法区分，不下结论**。

## 4. 对 76.8x 的含义

| 目标 | ms/step | 距 S3 天花板(117) |
|---|---|---|
| 76.8x 算术外推（标量口径，已作废） | 98.7 | **够不着** |
| 76.8x 算术外推（AVX2 口径，修正后） | **11.2** | **远远够不着（差 10x）** |
| B1 现状 | 559~571 | 4.87x 空间 |
| **B1 向量化 + bit-exact** | **~275** | 2.35x 剩余空间 |
| B1 无 gather 天花板 | 117 | — |

⇒ **即便把 B1 的 gather 成本降到零（物理上做不到），也只能到 117 ms/step。**
76.8x 所需的 11.2 ms/step **不是靠向量化能到达的**。
⇒ 这**加强**了 Lead 的结论：**转译器不是杠杆**（转译器连 gather 都改不了），
但也**修正**了「向量化能补上这个缺口」——它也补不满。

**能真正改变 117 这个天花板的，只有减少「累加次数」本身**，
即 §1 那条 bit-exact 契约要不要重谈：要么接受 S2 的非逐位（841/1536 分叉，
max|diff|=5.96e-8）换 ~166 ms/step（**不稳定，见 §2**），要么改算法减少连接数。
**这是产品决策，不是工程优化。**

⚠️ **一个我没有证据的说法，明确撤回**：我在给 Lead 的消息里写过
「优先确认生产路径真的调了向量化版（k0=20 时向量只覆盖 16/20=80%）」。
本探针证明 **S1 的 2.05x 已经包含了那 20% 标量尾块**（S1 测的是完整 k0=20）。
所以「先补尾块」**不是**剩余 2.35x 空间的主要来源 —— 那 2.35x 是 **gather 成本**
（S1−S3 = 0.336 ns/conn），不是尾块。**这条建议我在 §4 撤回。**

## 5. 我自己的两处失败（记录在案，因为都是「假数字」类）

### 5.1 S3 报了 `0.00000 ms`，而且我的守卫没拦住

第一版 S3 输出 `0.00000 ms  0.000 ns/conn`，外推表打出 `infx vs S0`。
**根因不是 consume 缺失**（我有 consume），而是：
S3 读 `w`/`xg`、写 `y3`，**三者在 reps 循环里全是不变量**，
而 `y3` 只在计时循环**之后**才被读 ⇒ **LLVM 把整个调用提到了循环外**，循环体变空。

**更值得记的是**：我的 `[FATAL]` 守卫当时**只打印**警告，
那个 `0` 仍然一路流进外推表 —— 守卫形同虚设。
修法：(a) 让每次迭代的输出成为下次迭代的输入（跨迭代真依赖）；
(b) 守卫把值置 `NAN` 并让格式化函数拦截（不再只是 println）。

**对比**：S0/S1/S2 没被提走，是因为它们经 **gather** 读内存，LLVM 无法证明可安全提升。
⇒ **S0 的正确性是运气，不是设计** —— 这一点比 S3 的 bug 本身更重要。

### 5.2 第一次在 d=128 上测，绝对值差 11.9x

初版默认 `--d 128`（怕标量 S0 太慢），得到 S0 = 47.6 ms/step，
与 Lead 的 566.8 差 11.9x。**这不是 bug**：`ns/conn` 在 d=128 与 d=1536 上
几乎相同（1.211 vs 1.185），但**每次调用的单位大小不同**，
乘同一个 15360 得到不同的 ms/step。
⇒ 教训：这个乘数（15360）**只在 d=1536 下有物理意义**，
换 d 必须同时报 ns/conn，否则绝对值不可比。已改为默认 d=1536。

## 7. 边界（未做到的事）

1. **本探针是独立复刻，不改 `core/src/b1_pure.rs`。** 结论适用于「若把 S1 的写法
   落到 b1_pure」的预期；**未在真实 `b1_forward` 上落地并跑 A1-A5 全套验收**。
2. **未测 k0=20 的标量尾块占比影响**。S1 里 `k0 % 8 = 4`，尾 4 条走标量
   （`while j < k0`），占 20%。这部分**已含在 S1 的实测里**（S1 是完整 k0=20），
   但未单独分离其贡献。
3. **S2 不稳定（1.82~3.44x），原因未查清**，只作量级参考。
4. **未测反向 `b1_backward`**。它的模式（`+=` 累加、写 dw）与 `sparse_gemm_bwd_w`
   同构，向量化空间可能不同 —— 本探针不回答。
5. **未测端到端 trainer**。117 ms/step 是「5 matvec × 24 层 × 128 位置」的外推，
   不含 attention/反向/optimizer。
