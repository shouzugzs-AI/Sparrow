## 1. P0：B1/B2 接入真实训练器

### 1.1 接入点与纪律

训练器是 `train/src/sparse_train24.rs`（3555 行）。原来它的稀疏算子**全部是算子版**
（`sparse_forward` = `compute_act_mask` + `sparse_accum`，反向是 `sparse_gemm_bwd_w` +
3 段手写掩码 dx 循环）。本轮加了一层 `--impl` 分派：

| `--impl` | 语义 | 前向 | dw 反向 | dx 反向 |
|---|---|---|---|---|
| **0** | **mask（默认，既有语义，行为逐位不变）** | `sparse_forward` | `sparse_gemm_bwd_w` | 手写掩码循环（逐字复刻） |
| 1 | `b1`：遍历全部 k0、无掩码 | `b1_forward` | `b1_backward` | `b1_backward_dx` |
| 2 | `b1fuse`：B1 + P1 融合反向 | `b1_forward` | `b1_backward_fused`（dw+dx **一次遍历**） | 同左 |
| 3 | `b2sh`：B2 SHARED（全层共享一次 top-k，**改变模型**） | `b2_forward` | `b2_backward` | `b2_backward_dx` |

**整体切换**是硬要求：6 个前向点（eval 3 + train 3）与 3 个 (dw,dx) 点必须走同一组
`sp_*` 入口。只切前向而反向仍读 `act`，会按**一张与本次前向无关的掩码**算梯度 ——
静默、且不会被任何维度检查发现（`b1_pure.rs:107-111` 的原话）。

### 1.2 前置缺口：B1 原来**没有 dx**

`b1_pure` 只有 `b1_backward`（dw）。没有 dx，梯度就传不到上一层 ⇒ 24 层里只有最后一层在学，
训练照样"跑通"、loss 照样降，但那不是深度训练。本轮补了：

| 新函数 | 位置 | 语义 |
|---|---|---|
| `b1_backward_dx` | `core/src/b1_pure.rs` | `dx[src] += dy[i]·w[i][j]`，**i 升序、j 升序**，无掩码 |
| `b1_backward_dx_scalar_reference` | 同上 | 逐位对拍基准（显式 f32 src） |
| `b1_backward_fused` | 同上 | P1：dw 与 dx **一次遍历** |
| `b2_backward_dx` | `core/src/b2_topk.rs` | B2 的 dx（只对被选中的 k 条），Shared/PerRow 两种 |

### 1.3 训练结果（200 步，四实现同配置）

| impl | 退出 | 判据 | 训练墙钟 | 其中周期验证 | **纯训练 tok/s** | 前向 tok/s | 反向 tok/s | 优化器 tok/s | 稀疏前向 | 稀疏反向 | train CE | val CE |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 0 mask | 0 | **16/0** | 91.76 s | 27.16 s | **24.8** | 34.1 | 101.2 | 968.6 | 34.6 | 102.5 | 4.1571→3.6765 | 4.1568→4.0575 |
| 1 B1 | 0 | **15/0** | 17.50 s | 1.48 s | **99.9** | 771.3 | 144.3 | 609.1 | 1132.7 | 146.9 | 4.1570→2.6005 | 4.1573→4.0515 |
| 2 B1+融合 | 0 | **15/0** | 10.28 s | 1.50 s | **182.2** | 765.2 | 416.8 | 608.4 | 1121.3 | 438.2 | 同上（逐行相同） | 同上 |
| 3 B2 SHARED | 0 | **15/0** | 24.63 s | 3.65 s | **76.3** | 247.2 | 137.3 | 608.6 | 275.5 | 139.7 | 4.1571→3.7386 | 4.1576→4.0706 |

口径：**纯训练 = step 循环墙钟 − 周期验证**（验证在 step 循环内部，见 §1.5）。
`tok/s = steps×batch×seq / 秒`；"稀疏前向/反向"= 5 个稀疏矩阵的桶累计（不含 attention/logits/AdamW）。

**关键倍速**：

```
B1 vs mask       : 纯训练 24.8 -> 99.9   = 4.03x    稀疏前向 34.6 -> 1132.7 = 32.7x
B1+融合 vs B1    : 纯训练 99.9 -> 182.2  = 1.82x    稀疏反向 146.9 -> 438.2 = 2.98x
B1+融合 vs mask  : 纯训练 24.8 -> 182.2  = 7.35x    稀疏反向 102.5 -> 438.2 = 4.28x
```

为什么 B1 的稀疏**前向**能快 32.7x（算术量反而多 2.5x）：mask 路径每次 `sparse_forward`
都要先算 `compute_act_mask` —— 在 k0=20 上做每行 top-8，实测那一步**就是全部成本**
（`P18-PROJ` 记录 0.4821 ms 掩码 vs 0.4767 ms 整体）。B1 没有掩码，只做 20 次乘加。

### 1.4 判据：ε 与确定性

新驱动 `vmlm-sparseb-bwd`（`train/src/sparseb_bwd.rs`）**11 判据全 PASS**：

```
E1 前向 ε（尺度 = Σ|w·x|）              = 1.383e-7  ≤ 1e-5   （位相同 724/1536 = 47.1%）
E2 B1 dw  vs sparse_gemm_bwd_w(k=k0)   位分叉 0 / 30720
E3 B1 dx  vs 标量参考                  位分叉 0 / 1536，累加次数 30720/30720
E4 融合 vs (dw + dx 分开)              dw 0 / 30720，dx 0 / 1536   ← **逐位等价**
E4-b 融合的标量参考也与分开一致        dw 0 / dx 0
E5 can-fail（漏最后一条 / dx 用 FMA）  抓到 1536/30720、959/1536、917/1536
E6 确定性（8 次重复）                  逐位相同
E7 B1 vs 算子掩码版(k=k0) ε            = 1.383e-7  ≤ 1e-5
E8 P1 计时（融合 vs 分开）             1.554x（隔离内核口径，见 §2.3）
E9 B2 SHARED dx vs 独立标量参考        位分叉 0 / 1536，且只对被选中的 12288 条累加
```

**训练级确定性**：同样的命令跑两次，`train curve` / `val curve` / `FINAL` **逐行相同**
（impl1 与 impl2 各自验证）；且 **impl1 与 impl2 的 loss 曲线逐行相同** —— 融合在整条
24 层训练轨迹上数值等价。

### 1.5 顺手修掉的三处既有缺陷（都不是本轮引入的）

1. **`proj_dw[l][pi]` 跨 step 无限累积**（真缺陷）。`ffn_dw_all[l]` 每步清零，
   而 96 个投影梯度缓冲**只在分配时清零**，之后 `+=` 一直累加 —— 于是每步的更新用的是
   **历史所有步梯度之和**。`clip_grad` 会把它归一化到 norm 1，所以"看起来也能训"。
   已改为与 FFN 同口径：每个 step 开头清零，batch 内累加。
2. **每步白写 37.7 MB**：`zero(gwp, 4*d*d)`，而 `gwp` 自 P18-C 之后**没有任何写入方**
   （`let _ = gwp;`）。已删除该行（行为中性）。
3. **口径缺陷：周期验证被算进"训练墙钟"**。`eval_loss` 在 step 循环内部
   （`if st % 10 == 0`），却不属于任何 prof 桶 —— mask 路径 200 步里它占
   **27.2 s / 91.8 s（30%）**，而 B1 路径只占 1.5 s。现在它单独计进 bucket 8，
   并同时报"训练墙钟"与"**纯训练**"两个数。这一条直接改变了结论的量级
   （mask 17.4 → 24.8 tok/s），所以必须写明。

另外：B1 模式下 `act` 全程保持初始值 1.0（`conn_train.rs:342`），于是
`sparse_adam_step` 对所有 k0 条生效 —— 正是 B1"全部连接都算"的语义。
唯一受影响的判据是 `STATS top-k genuinely skips some connections`：B1 **没有 top-k**，
该判据在此实现下**无定义**，已显式标 `[N/A]` 并**不计入 checks**（checks 15 vs 16 的来源）。

## 2. P1：融合前向 + 反向

### 2.1 先纠正一个前提：三合一在标准调度里不存在

任务书设想「对每个 (i,j) 同时做 y += w·x / dw = dy·x / dx += dy·w」。但
**`dy` 是整网前向 + loss 之后才有的量** —— 在 (i,j) 被访问的前向时刻它还不存在。
所以「前向 + dw + dx 一次遍历」只有在**重算激活（activation recomputation）**的调度下
才成立；本项目没有这种调度。

**可以真正落地、并且确实共享遍历的是 `dw` 与 `dx`**：两者都在 `dy` 已知之后执行，
共享 `src` 与 `dy[i]`，且 `x`（dw 用）与 `w`（dx 用）各只需读一次。分开写就是两遍遍历。
本轮交付的是这个二合一，并把"三合一做不到"作为结论写下来，而不是假装做到了。

### 2.2 实现与逐位论证

`kernels::b1_backward_fused_dwdx_avx2`：**dw 走向量（gather + 广播），dx 走标量**
（AVX2 没有 scatter，这是物理限制不是偷懒）：

```
dw[i*k0+j] += dy[i] * x[src[i*k0+j]]     ← 向量，mul + add，**不用 FMA**
dx[src]    += dy[i] * w[i*k0+j]          ← 逐通道标量，i 升序、j 升序
```

逐位论证：dw 每个元素一次 mul 一次 add（无 FMA、无重排）⇒ 与标量 `+=` 逐位相同；
dx 是逐通道标量、顺序与手写参考完全一致。**判据 E4 实测：dw 0/30720、dx 0/1536 分叉。**
也就是说 P1 的验收不是任务书要求的 ε≤1e-6，而是**逐位**（更强）。

### 2.3 速度

| 口径 | 分开（dw + dx 两遍） | 融合（一遍） | 加速 |
|---|---|---|---|
| 隔离内核（`vmlm-sparseb-bwd` E8，QPC 中位数） | 0.050500 ms（1.644 ns/conn） | 0.032500 ms（1.058 ns/conn） | **1.554x** |
| **训练器里的稀疏反向**（200 步 × 24 层，含 cache 冷启动） | 10.895 s → 146.9 tok/s | 3.651 s → **438.2 tok/s** | **2.98x** |
| **纯训练** | 16.017 s → 99.9 tok/s | 8.782 s → **182.2 tok/s** | **1.82x** |

两个 2.98x / 1.554x 都对：隔离口径是**热 cache 单矩阵**，训练器口径是**120 个矩阵轮转**，
后者的两遍遍历各自的 cache 代价更高。口径必须随数字报，不能混用。

任务书预测「训练 tok/s 提升 1.5–2x」→ 实测 **1.82x**，在预测区间内；
「内存加载次数减少 ~2.3x」→ 稀疏反向实测 **2.98x**（因为除了加载次数，还省掉了
一遍 `src`/`dy` 的读取与循环开销）。

## 3. P1-b：转译器主动复用 —— 先做扇出统计（任务书要求）

新驱动 `vmlm-sparseb-fanout`（只统计，不实现），在真实的 120 个矩阵拓扑上：

### 3.1 两个必须分开的量

| 量 | 定义 | 实测 | 能否兑现 |
|---|---|---|---|
| **全局扇出** | 整个矩阵里 `x[s]` 被几条连接用到 | 均值 = k0 = **20**；77.5% 的源扇出在 17–32 | **不能**：1536 个源放不进 16 个寄存器，同一源的 20 次使用在 1536 行上相距几十万条指令 |
| **窗口扇出** | 连续 W 行内出现的**不同源数 D**（C = W·k0） | 见下表 | 这是转译器能兑现的量 |

```
    W(行)      C=W*k0 连接        D 不同源    (C-D)/C 上界   D<=16 窗口
       8        3686400          152.0         4.99%          0.0%
      16        3686400          288.9         9.70%          0.0%
      32        3686400          523.6        18.19%          0.0%
      64        3686400          868.9        32.12%          0.0%
     128        3686400         1246.4        51.31%          0.0%
     256        3686400         1481.3        71.07%          0.0%
```

### 3.2 寄存器受限上界（决定性的那一列）

`(C−D)/C` 假设**无限寄存器**。真实约束是 16 个 ymm 还要留累加器：

```
    W(行)       R=4 可省       R=8 可省      R=12 可省      R=16 可省
       8        2.64%        4.45%        4.95%        4.99%
      16        1.87%        3.14%        4.39%        5.64%
      32        1.48%        2.72%        3.87%        4.77%
      64        1.15%        2.10%        3.02%        3.86%
     128        0.90%        1.68%        2.40%        3.05%
     256        0.71%        1.34%        1.93%        2.49%
```

### 3.3 判决：**不做**

* 现实预算 **R=8（8 个缓存 + 8 个累加器）** 下，最好只有 **4.45% < 5%**（任务书自己的门槛）；
* 唯一 >5% 的格子是 **R=16**，而那时**一个累加器都不剩**，不可实现；
* **`D≤16` 的窗口占比 = 0.0%**（所有 W）—— 任务书设想的"整窗的源都驻留寄存器"**从不发生**；
* 代价侧：按源重排会**改变每行的累加顺序**（破坏 B1 的逐位契约），而收益 ≤4.4%。

⇒ **「转译器主动复用」在本拓扑上不值得做。** 这不是"实现太难"，是**收益上界就低于门槛**。
（如果将来 d 增到 20480，D/C 会下降，那时需要重跑本统计 —— 这正是 P3 的触发条件。）

## 4. P2-b：decode tok/s（batch=1，逐 token 生成）

新驱动 `vmlm-sparseb-decode`：24 层 × 5 稀疏矩阵（B1）+ 因果注意力 + KV 缓存，
权重确定性随机初始化，greedy 解码。

| 上下文 | prefill | **decode（KV-Cache）** | ms/token | decode（无 cache） | KV 加速比 |
|---|---|---|---|---|---|
| ctx=128 | 359.8 tok/s | **237.8 tok/s** | 4.204 | 2.8 tok/s | 85x |
| ctx=512 | 163.8 tok/s | **92.5 tok/s** | 10.813 | 0.3 tok/s | 290x |
| ctx=2048 | 6.3 tok/s | **3.1 tok/s** | 323.2 | ~0.0 tok/s | 1001x |

**prefill 与 decode 是两个口径，不可混报**：prefill/decode 比在 1.5–2.0x。

**decode 被什么限制（分相计时，--profile）**：KV 缓存流量随上下文线性增长：

```
ctx=128 : KV cache 36.6 MB/token     ctx=512 : 144.6 MB/token     ctx=2048 : 576.6 MB/token
稀疏 B   : 恒为 ~0.70 ms/token（120 次 B1 matvec，与上下文**无关**）
```

⇒ decode 的耗时几乎完全由 **KV 缓存带宽 + attention** 决定，**不是**由稀疏 B 决定。
稀疏 B 单独口径的 decode 上限 = 1 / 0.70 ms/token ≈ **1430 tok/s**（与 ctx 无关）。

**必须一起报的边界**（否则这组数字会被误读）：
1. 本驱动的注意力是**我自己写的** dot/SAXPY（单累加器、无分块、无多累加器），
   实测每 token 的 KV 流量只有 **~1.9 GB/s** 的有效带宽 —— 这不是 VMLM 引擎的能力，
   是**这个探针**的能力。所以上表是**下界**，且**不能用它和 llama.cpp 比**。
2. 位置 0 的 logits 已确认为有限数（`finite=true`）；第一版无归一化时实测 `sink=NaN`
   （24 层纯残差数值爆炸），而 NaN/denormal 可能走慢路径 **污染 tok/s**。现已加
   残差缩放 1/√2（只影响数值有界性，不改变任何算子调用次数与访存模式）。
3. ctx=2048 的 323 ms/token 与 1.9 GB/s 的有效带宽一致（577 MB / 0.323 s）；
   本机 16 GB RAM、空闲 10.6 GB，**不是 swap**。

## 5. P2-a：同算力稠密对照（回答「效率是否转化为智能」）

新驱动 `vmlm-sparseb-dense24`（**DENSE-REF，对照物而非生产路径**）：24 层稠密模型，
**逐字复制** `sparse_train24.rs` 的数据生成器与 split 种子（同文法、同 x0 值域、
同 `0xDA7A_0003 / 0xDA7A_9A9A` 种子）⇒ 两个模型看到的是**同一批序列**；
超参同规则（`s=sqrt(3/fan_in)`、`Wo/Wf` 乘 `1/sqrt(2L)`、逐组 clip=1、Adam(0.9,0.999)、
lr=0.003·sqrt(2/L)·sqrt(128/d)）。

### 4b.1 先证明反向是对的（否则 loss 曲线没有意义）

一个**错的反向**也会让 loss 下降（Adam 归一化幅度），本项目有过先例。所以先做
`DENSE-0` 数值梯度自检（中心差分 vs 解析）——它当场抓住了一个真 bug：

> 三个 `dW` 累加把 `[T×d]` 的激活直接传给了 `gemm_nt`（它按 `[m×k]` 取数）⇒
> 读错元素。表现是 **Wf 探针 rel=4.9e-2、Wq 解析梯度恰好全 0**，不崩、loss 照降。
> 修法：`outer_accum` 先把两个 `[T×d]` 转成 `[d×T]` 再走 `gemm_nt`。

修好后的判据（21 个探针，layer0/layerL 的 Wq/Wo/Wf + emb，各取 |grad| 最大的条目）：

```
Wo/Wf/emb 探针：rel = 1e-6 ~ 5e-4，SNR = 380 ~ 2600   -> 完全吻合
Wq 探针      ：|grad| ~ 1e-5（比 Wo/Wf 小 3 个数量级，因为 q 只经 softmax 影响输出，
              初始化时注意力接近均匀）；SNR ≈ 0-2，属 **f32 分辨率受限**
  判别（不是猜）：eps 0.05 -> 0.5 -> 2.0 时 rel 单调下降
                  Wq(lL): 0.114 -> 0.0020 -> 0.0001
                  Wq(l0): 0.589 -> 0.0141 -> 0.0071
  噪声受限的 rel 随 eps 下降（FD 噪声 ∝ 1/eps），真错不会 —— 所以是噪声不是 bug。
```

### 4b.3 结论（数据说话，边界一并说）

1. **算力匹配（0.997x）下：稠密在墙钟上快 2.4x（3.43 s vs 8.78 s），但验证 CE 明显更差**
   （4.916 vs B1 的 4.052，差 0.86 nats；val PPL 136.4 vs 57.5）。稠密模型
   val CE **高于初始值** ⇒ 它在这个任务上只记住了训练集。
2. **即使把墙钟预算给到 B1 的 0.92x、算力/参数给到 2.55x**（d'=280），稠密仍以
   4.819 vs 4.052 落后。d'=390（4.95x 算力）更差（5.215），且**默认 lr 下直接发散**。
3. 降低稠密侧 lr 能让它**更拟合训练集**（train 3.48→2.89）却让**验证更差**
   （4.92→5.43）：说明稠密侧的问题不是"没训够"，是**过拟合**。
4. **必须说明归因边界**：B1 的优势不能简单归给"稀疏"。在**参数匹配**时，
   稀疏模型的残差流/注意力宽度是 **1536**，而稠密只有 **175** ——
   也就是说"同参数量下宽度可以大 8.8 倍"才是它的结构优势（这正是
   `sqrt(d·k0)` 这条匹配关系的含义）。要区分"稀疏"与"宽度"的贡献，
   需要再做一组**同宽度**对照（例如稀疏 d=1536 对比稠密 d=1536），那是另一个实验。
5. 另一个必须说的口径事实：**稠密 AVX2 每个 MAC 比稀疏 gather 内核便宜约 2.6x**
   （同样算力稠密只需 1/2.6 的墙钟）。所以"同算力"必须声明是**算术匹配**还是
   **墙钟匹配** —— 上表两种都给了，结论在两种口径下方向一致。
6. 样本量边界：**单任务、单种子、64 条训练序列、200 步**。它足以回答
   "这个对照配置下谁更好"，不足以给出普适结论。

## 7. 未做到（不许淡化）

1. **P2-a 只做了"参数/算力匹配"与"墙钟匹配"两组，没做"同宽度"对照。** 要区分
   「稀疏」与「同参数量下宽度大 8.8 倍」这两个因素的贡献，需要一组**同宽度**对照
   （例如稀疏 d=1536 对比稠密 d=1536，此时稠密算力是 5·1536²/153600 = 76.8x）。
   这是本次结论里最大的未闭环之处（见 §4b.3 第 4 条）。
2. **P3/P4 未开始**（源聚类、按源遍历、从稠密映射、功能接口表、B2 语义决策）。
3. `--impl 3`（B2 SHARED）**改变了模型**（全层共享一次 top-k），它的 76.3 tok/s 与
   loss 只能当作**另一个模型的读数**，不能与 B1 直接比优劣。
4. decode 的注意力内核是探针级的（见 §4 边界 1），所以 §4 的表**不能**用于与常规引擎对比。
5. 训练规模仍然是玩具级（vocab=64、合成语言、batch=1、seq=8、200 步、单种子）。
   P0 证明"训练闭环跑通 + 数值/吞吐可测"；P2-a 的对照组结论也只在这个规模上成立。
6. 本轮踩到并修掉的一个**自身工具坑**：用 `Get-Content | Set-Content` 做 UTF-8 文本
   往返会把中文注释双重编码损坏（并且吞掉换行）—— 修法是**整文件重写**。
   教训与项目既有的"S1 落地事故"同类：**探针/工具本身出错比被测代码出错更难发现**。
   同类还有两处（都留在报告里）：decode 探针第一版 `sink=NaN`（24 层纯残差数值爆炸，
   NaN 可能走慢路径污染 tok/s）、以及稠密缓冲 `cap=ctx` 导致的堆损坏（0xC0000374）。
