# P28：调用计数 + 瓶颈报告（`--calls` / `_opt/prof_bottleneck.ps1`）

目标：**直观、低开销**地回答三个问题 —— 谁被调用了多少次？每步时间花在哪个相位？
训练循环里到底有没有文件 I/O？并且这个东西要能挂进现成的扫描脚本里。

---

## 0. 摘要（本轮实测的结论）

| # | 结论 | 证据 |
|---|---|---|
| 1 | **训练循环里每步 0 次文件打开**；读盘只在启动（3 次 / 143.2 MB），写盘 4 次（metrics/curve/train_log/summary） | 计数器 `文件读-打开次数`/`文件写-打开次数` 的 per_step = 0；`文件读-字节` 一次性 150,195,524 B，与进程级 `ReadTransferCount` 143.2 MB 独立吻合 |

## 1. 为什么不写"采样 profiler"

* 这个引擎是**手写标量/AVX2 内核 + 4 个 region 并行**：采样火焰图会把 4 个 worker 的栈混在一起，
  在"每步 4 次 `b1.backward`、每步 51 次 `opt_step`"这种结构量上几乎没有分辨力；
* 本机没有 `xperf`/`wpr`/Linux `perf`；
* 真正能直接指导优化的信息是**结构**（次数、元素数、文件次数、相位占比），而这些用
  relaxed 原子加就能拿到，**开销有上界**（每步计数合计 ~70 次 × 2 ns = 0.14 µs/步，
  占 1.3 s 的 0.00001%）。

## 2. 实现（`train/src/b1_full_train.rs`，`--calls 0|1`）

32 个槽位的计数表 + 两个内联函数：

```rust
#[inline(always)] fn cput(i: usize)        // 计一次
#[inline(always)] fn cadd(i: usize, n: u64) // 计 n 个（元素数/字节数/token 数）
```

插桩点（都是**粗粒度入口**，不是逐元素）：

| 计数器 | 插在哪 | 为什么值得数 |
|---|---|---|
| `step_fn(train/eval)` | region 入口 | region 切分是否等于线程数 |
| `b1.forward(整段前向)` / `b1.backward` | 每个 region 每步一次 | 与相位表配对算"每调用耗时" |
| `head_bwd_batched` / `par_head_bwd` / `par_b1_backward` / `head_gemm` | 各分支 | 确认走的哪条内核路径（这次确认是 `head_bwd_batched`） |
| `CE块` / `CE计分位置` | CE 循环 | 掩码是否生效（P27 的 `--sft-from` 就靠它证明 32/32） |
| `opt_step` / `opt_step元素数` | `opt_step()` 入口 | 元素数**必须等于参数量**，否则有张量漏更新 |
| `clip_grad` / `clip_grad元素数` | `clip_grad_c()` 包装 | 每张量一次裁剪，与 opt_step 同数 |
| `par_for` / `repack_head_wt` / `alloc` / `alloc元素数` | 同名函数 | 每步的调度/重打包/分配次数 |
| `文件读-打开次数` / `文件读-字节` / `文件写-打开次数` / `文件写-字节` | `read_u32_file`、`meta.json`、`ck_read`、`ck_write`、各 CSV/summary 的 `File::create` | 回答"是不是 I/O 瓶颈" |
| `checkpoint载入` / `checkpoint保存` | `ck_read`/`ck_write` | 长跑里周期落盘的开销 |

**不计数**（明确说清，别以为漏了）：`zero`/memset、内核内部的逐元素操作、stdout 字节数、
syscall 条数、Rust `Vec` 的分配（走系统分配器，不在 `alloc()` 里）。

输出：stdout 一张按次数降序的表 + `{out_dir}/calls.csv`（自动化脚本直接读这个，不解析文本）。

**正确性硬证据**（同一配置 1500 步）：

| 运行 | `loss_hash` | 结论 |
|---|---|---|
| `--calls 0`（默认） | `0x373320f16bee8935` | 与加计数器之前**逐位相同**（默认路径没变） |
| `--calls 1` | `0x373320f16bee8935` | **插桩不改变数学**（同一个 hash） |

## 3. 自动化：`_opt/prof_bottleneck.ps1`

一条命令出报告，内部做三件事（都不改动被测程序）：

1. **N 步 vs 2N 步**（同 seed，前 N 步完全一致）⇒ 把每个计数分解成
   `per_step` 与 `one_time`。**没有这一步，"289 次启动 alloc"会被误读成"每步 14 次 malloc"**——
   第一版就差点这么读。
2. **相位表**（`--profile 1`）按 `nslot` 摊平到 wall，并给出"未统计"残差。
3. **交错配对**跑 `--calls 0/1` 实测插桩开销（实测 3 轮中位比值 0.9875、离散度 1.1% ⇒ 开销在噪声内）；≥3 轮才允许下结论
   （2 轮的 MAD 恒为 0，会伪造出"σ=0.00% 的显著差异"，这是踩过的坑），否则只给理论上界。

判据是**可失败**的（次数与配置应有值对账，不符就报 flag）：`step_fn/backward = nslot`、
`opt_step/clip = 层+3+4·n_attn`、`par_for = 1/步`、训练循环内文件打开 = 0、每步 alloc = 0。

用法：

```powershell
& .\_opt\prof_bottleneck.ps1 -Config prod  -Steps 30 -Rounds 3     # 生产几何（dim4096/L32/batch32）
& .\_opt\prof_bottleneck.ps1 -Config small -Rounds 3               # dim512/L4，300 步只要十几秒
# 报告写到 _opt\prof\<Tag>\report.md，原始计数 _opt\prof\<Tag>\runs\*\calls.csv
# 顺手挂进扫描：& .\_opt\run_sweeps.ps1 -WithProfile
```

## 4. 实测结果

### 4.1 生产配置（dim4096/L32/batch32/seq64，4 线程，`--pin 1`）

调用结构（30 步 vs 60 步分解）：

| 计数项 | per_step | one_time | 对账 |
|---|---|---|---|
| `opt_step元素数` / `clip_grad元素数` | **1,704,224** | 0 | = params total ✓ |
| `opt_step` / `clip_grad` | 51 | 0 | 32+3+16 ✓ |
| `取批token` | 2,048 | 0 | batch×seq ✓ |
| `CE计分位置` | 2,016 | 16,128 | 2048×(63/64)=2016 ✓；一次性 16128 = 启动时 8 次 eval × 2016 |
| `b1.forward` / `b1.backward` / `step_fn(train)` / `head_bwd_batched` | 4 | 8 | = nslot ✓ |
| `par_for` / `repack_head_wt` | 1 | 1 | ✓ |
| `alloc` / `alloc元素数` | **2** / 8 | 249 / 985,398,401 | ⚠️ 每步 2 次 malloc（见 §0 #2） |
| `文件读-打开次数` / `文件读-字节` | **0** / 0 | 3 / 150,195,524 | 读盘只在启动 ✓ |
| `文件写-打开次数` | **0** | 4 | 无 per-step 写 ✓ |

相位（30 步 × 2 轮，按 nslot 摊平）：

| 相位 | ms/步 | 占 wall |
|---|---|---|
| 逐层反向 | 799.0 | **60.7%** |
| 前向（嵌入 + 32 层 + head 一整段） | 416.2 | **31.6%** |
| head 反向 | 14.8 | 1.1% |
| 嵌入反向 | 14.3 | 1.1% |
| CE/softmax | 8.3 | 0.6% |
| 优化器 + clip | 2.27 | 0.17% |
| 未统计（取批 + 线程同步 + 逐层前向计时点缺口） | — | 4.7% |

> 注意 `--sparse-io 1` 时**相位 0 永远为 0**：稀疏路径把"嵌入+逐层+head"整段前向都记在相位 1
> （`tm` 在 `step_fn` 入口才新建，之后直到 `if io_sparse { add(1) }` 才第一次记账）。
> 所以表里"前向"= 整段前向，不是"只有 head"。（这一点上轮报告 §4.3 写错过，已修。）

### 4.2 小配置（dim512/L4/batch16，300 步）

| 相位 | 占 wall |
|---|---|
| 前向（整段） | 35.3% |
| 逐层反向 | 30.1% |
| head 反向 | 14.5% |
| 嵌入反向 | 12.8% |
| CE | 9.6% |
| 优化器 + clip | 1.5% |

规模一小，**head 反向/嵌入反向/CE 的占比立刻从 2.7% 涨到 36.9%** ——
这些是"与词表/维度相关、与层数无关"的项（head 131K 参数 = 层的 32 倍），
所以"层数越浅，head/embed 越主导"。这也解释了为什么 Adam/SGD 的差别在两种配置下都不显眼。

## 5. 已知不精确（写清楚，不装作精确）

1. 相位表按 `nslot` **整除摊平**，region 之间并不完全同步 ⇒ "未统计"可能是负数（小配置 -3.85%），
   脚本里已钳到 0 并在报告注明；偏差量级 ~5%。
2. `CE计分位置` 含 eval 的窗口（一次性部分单列），所以它的 per_step 略高于 `tokens×63/64`。
3. `alloc` 只统计引擎自己的 `alloc()`，**不含 Rust `Vec`/`String` 的分配** ⇒ "热路径分配"的下界。
4. 计数器是全局的（不按线程分）⇒ 能看到"每步 4 次"但看不到"哪个 worker 慢"；
   要看负载不均得用相位 × 每 worker 单独的计时（本轮没做）。
5. 只统计了**函数级**调用，没有指令级计数（那需要 perf 类工具，本机没有）。

## 7. CRT 假说检验（`_opt/prof_crt.ps1` / `prof_crt2.ps1`）

假设："瓶颈在 CRT（系统分配器 / 线程同步 / 主线程串行段）"。三层分别测，全部**否**。

### 7.1 CRT 堆（`GlobalAlloc` 计数，'文件读/写' 那一节之外的新增 `CRT *` 计数器）

| 计数项 | per_step | one_time（启动） |
|---|---|---|
| `CRT malloc` | **613** | 4,927 |
| `CRT free` | **613** | 4,890 |
| `CRT realloc` | **104** | 851 |
| `CRT malloc字节` | **63,920 B** | 460.7 MB |

→ 每步 0.064 MB 的堆流量。按"malloc+free 一对 200 ns"（Windows 带堆锁的保守值）算
= **123 µs/步 = 0.008%**；按 1 µs/对算 = 0.6 ms = **0.04%**。**不是瓶颈。**

> 这也修正了本报告 §0 #2 的说法：`alloc` 每步 2 次只是**引擎自己的**分配；
> Rust 的 `Vec`/`collect` 走 CRT，真实数字是 **613 次/步**。不过量级上仍可忽略。

### 7.2 主线程串行段（相位 6，本轮才插桩）

相位 6（取批 + 零梯度 + 梯度归约 + 重打包）此前**从未被记录**（表里恒为 0）。本轮插桩后实测：

| threads | 相位 6 / 步 | 占 wall |
|---|---|---|
| 1 | 0.2 ms | 0.005% |
| 4 | **1.8 ms** | **0.1%** |
| 8 | 3.6 ms | 0.2% |

→ 串行段不是瓶颈；之前"未统计 4.7%"主要是**相位按 region 求和**造成的口径差，不是串行工作。

### 7.3 线程扩展性（batch=32，修正了 `--threads` 被 BASE 抢先匹配的 bug）

| threads | nslot | ms/步 | 加速比 | 忙核（进程 CPU/wall） |
|---|---|---|---|---|
| 1 | 1 | 3858 | 1× | 0.95 |
| 2 | 2 | 2308 | 1.67× | 1.58 |
| 4 | 4 | 1625 | **2.37×** | 2.42 |
| 8 | 8 | 1717 | 2.25×（**无增益**） | 3.93 |

机器是 **i3-12100F（4 核 8 线程，3.3 GHz）**。8 线程能跑到 3.93 核 ⇒ 4 个物理核是能被喂满的，
所以不是"OS 不给核"。**4→8 无增益**说明 4 核已经饱和 ⇒ 瓶颈在**核内的每 token 效率**，不是线程数。

### 7.4 相位表的口径修正（重要）

| 运行 | 相位总和 / wall |
|---|---|
| threads=1（nslot=1） | **1.11** ⇒ 单 region 时相位表 ≈ wall，可信 |
| threads=4（nslot=4） | 3.55 ⇒ 相位是**每 region 各记一份**，比值 = 同时处于该相位的 region 数 |
| threads=8（nslot=8） | 6.60 ⇒ 区域内部并行度 83%（t4 时 89%） |

⇒ 相位总和**不能当"工作量"读**（它随 nslot 线性增长），只能当"相位占比"读。
而且相位 0 在 `--sparse-io 1` 路径下永不被记账（整段前向记在相位 1）。

### 7.5 结论

CRT 三项（堆 613 次/步、串行段 1.8 ms、同步）合计 **< 0.15%**。
真正的位置：**每个 token 在 forward/backward 内核里只跑到 ~12.2 GFLOPS（4 线程 FP32 峰值的 ~6%）**，
4 个物理核已饱和、再加线程无收益 ⇒ 瓶颈是内核的指令级效率（稀疏 gather、短点积、反向标量路径）。
下一步该做的是内核 tile/ILP 审计（P20 那一套），而不是换 CRT 或加线程。

> 顺带记一个测量陷阱：`loss_hash` 是对**被记录的 loss 曲线**做哈希，
> 所以 `--log-every` 不同的两次运行 hash 必然不同 —— 本轮的"hash 变了"是我把 `--log-every 25` 写成 999 造成的，
> 改回来后仍是 `0x373320f16bee8935`（PASS）。做逐位回归时日志参数必须一字不差。

## 8. t8 令牌分块进生产：**被实测否证**（2026-10-17 深夜，2 轮交错 × 80 步）

提案①"把令牌分块搬进生产路径"的实测结果：**没有收益，是净损失**。

| 臂 | r1 ms/步 | r2 ms/步 | 同轮配对比值 | 数值 |
|---|---|---|---|---|
| t8 关（基线） | 1236.25 | 1331.25 | 1.00 | `0x4abe7f9b…` |
| t8 整栈（stack=1） | 1857.5 | 1856.25 | **1.39~1.50（慢 45%）** | 同基线 |
| t8 逐层 drop-in（stack=0） | 2780 | 2853.75 | **2.14~2.25（慢 2.2×）** | 同基线 |
| t8 只开反向 | 1825 | —（作业中止） | 1.48（单轮，不下结论） | 同基线 |

- **数值等价**：四臂 `loss_hash` 完全相同 ⇒ t8 的数学没问题，纯粹是性能问题。
- **机制（代码级）**：`b1_layer_forward_t8`（`ops/src/b1_pure.rs:527`）每层做 **2 次完整转置**
  （`transpose_t8_avx2(x,[t×d])` + `transpose_t8_back_avx2(y,[d×t])`）⇒ 32 层 × 2 = 64 次/步/region，
  每次 [512×4096] f32 = 8 MB 读 + 8 MB 写 ≈ 1 GB/region/步的转置流量 ⇒ 就是慢的来源。
  整栈路径（`models/src/model.rs:264`）只在**注意力边界 + 头/嵌入**处转置（约 9 次/步），
  所以比 drop-in 好，但**仍然比 token-major 慢 45%** ⇒ 即便摊薄了转置，t8 链在
  `dim=4096 / tt=512 / k0=8` 的形状上也没有跑赢现有内核。
- **结论**：探针里"令牌分块 4.51×"（`docs/B_速度优化_tok_s验收.md`）是**微基准**（热缓冲、无转置、
  同一份 xt 反复用），**不能迁移到训练器**。这条路上要真赢，必须让**整网原生跑在 dim-major 布局**
  （连 attention 和 head 一起，零转置），那是布局级重写，不是开关级改动。
- 顺带确定的基线：**边际步时 1230 ms/步**（15/60/120 步三点求边际：15 步平均 1440 是被
  3.9 GB 缓冲首次触碰的缺页抬高的）⇒ 短跑（<30 步）测速必须用边际值或 ≥80 步，否则误差 15%+。

### 8.1 资源纪律（本机同时有别的重活，例如显卡库开发）

新增 `_opt/lowprio_run.ps1`：**等空闲 → BelowNormal 优先级跑 → 运行中监控外部负载**。
- 启动前：连续 2 次采样系统总 CPU < 15% 才启动（最多等 30 min）；
- 启动时：`PriorityClass = BelowNormal`（不是 Idle —— Idle 会把自己饿死，计时变成"被抢占时间"）；
- 运行中：每秒采总 CPU%，用「总负载 − 自身负载」估**外部负载**；外部负载 > 25% 记为
  `CONTAMINATED`，此时**绝对 ms/步 不可用于跨条件比较**，只能用同轮相对比值或重跑。

t8 只开反向那一臂用它补测（80 步）：

| 臂 | ms/步 | 外部负载 max/mean | 判 |
|---|---|---|---|
| t8 关 | 1485 | 48.3% / 10.7% | CONTAMINATED |
| t8 只开反向 | 1846 | 43.0% / 11.4% | CONTAMINATED |

同轮相对比值 = 1846/1485 = **1.24×（更慢）**，与 r1 的 1.48× 一致；两臂 `loss_hash` 仍相同。
⇒ 结论不变：**t8 的任何组合在训练器里都是净损失**，且这组绝对步时因被外部负载污染（1485 vs
空闲时的 1230-1330）已标注不可作基线。
