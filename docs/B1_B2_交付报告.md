## 2. B1 交付（步骤 2，已完成）

**PATH: B1** — 模块 `core/src/b1_pure.rs`，函数 `b1_forward` / `b1_backward`。
判据名 `test_b1_bit_exact`（`train/src/b1_verify.rs:211`）。

### 2.1 定义（任务书第四部分，逐字实现）
```
for each neuron i:
    acc = 0
    for j in 0..k0:                 // k0=20，全部计算
        acc += w[i][j] * x[src[i][j]]
    y[i] = acc
```
无 top-k、无掩码、无筛选。累加契约：**升序 j、单标量累加器、首项直接赋值**。

| 判据 | 结果 | 实测 |

| A2 零掩码证明 | **PASS** | 前向期间 act[] 被写 **0** 次（哨兵位型快照，can-fail 对照 =1） |

| A4 性能 | **PASS** | b1 = **0.0363 ms** vs 算子版 **0.2341 ms** ⇒ **6.45x** |
| A5 反向 bit-exact | **PASS** | vs `sparse_gemm_bwd_w`：**0/30720** |

**两套独立实现互证**：Lead 的 `vmlm-lead-b1` 与 b1-builder 的 `vmlm-b1-verify`

### 2.3 判据强度（b1-builder 额外做的 `vmlm-b1-canfail`）

A1 报 `bad=0` 有「判据恒真」这个替代解释，所以把 6 种**已知错误实现**喂进去：
```
wrong-1 漏算最后一条(k0-1)        caught 1536/1536
wrong-2 跳过第一条(j从1起)        caught 1536/1536
wrong-3 行内降序累加              caught 1196/1536   <-- 最重要
wrong-4 从0.0起加(随机数据)       caught 0           <-- 如实报告的边界
wrong-5 错行宽(k0+1)              caught 1536/1536
wrong-6 交换乘数顺序(x*w)         caught 0           <-- 本该为0
```
- **wrong-3 是关键**：连接集合相同、MAC 数相同、数学等价，只有**累加顺序**不同，
  仍 **1196/1536 行位型分叉** ⇒「累加顺序是契约」是**实测**，不是口号。
- **wrong-4 随机数据抓不到**：`0.0+t == t` 对绝大多数 t 成立。所以 A1 里有一条
  **定向构造**（`k=1, w=-0.0`，实测 `neg_zero(b1)=4 / from0=0`）。
  **随机对拍不足以覆盖这条契约** —— 这是本轮最值得留档的方法论结论。
- **wrong-6 抓到 0 是正确的**：IEEE-754 乘法交换律成立，该维度本就不可观测。
  探针把它断言成 `==0` 并注明理由，防止后人误以为漏检去"修"没问题的代码。

### 2.4 B1 完善（第二轮）：修掉一个真实覆盖漏洞 + 两处模块缺陷

**这一节记录的是「B1 验收通过之后」才发现的缺口 —— 这正是"判据必须能失败"的价值。**

#### (a) 🔴 `b1_backward` 的 `+=` 契约**没有被任何判据覆盖**

模块头把「反向必须用 `+=` 累加而不是赋值」写成一条极重要的契约，理由是：
> 改成赋值会让一个 batch 里多帧的梯度互相覆盖，而 loss 仍会下降（只是慢），
> 于是这个 bug **极难被发现**。

但原 A5 从**清零的** `dw` 出发 —— 在那个输入下 `dw = g*x` 与 `dw += g*x`
**给出完全相同的结果**。也就是说 A5 报 `bad=0`，**无法区分这两种语义**。
⇒ **一条被文档写成「极难发现」的契约，却没有判据能发现它。**

**已补判据 A5-b**（4 条），并且做了**注入验证**：

| | 注入前（正确实现） | 注入 `=` 之后 |
|---|---|---|
| A5（原判据，从零清零缓冲） | PASS `bad=0` | **仍然 PASS `bad=0`** ← 证明它对这个问题全盲 |
| **A5-b（新判据，预置非零缓冲）** | PASS `bad=0` | **FAIL `bad=30720/30720`** ✓ |

修法：预置一份**非零** `dw`，跑一次后要求结果等于「预置值 + 本次梯度」，
参考用**独立手算**（朴素标量循环），而不是拿实现和自己的另一种调用方式对拍。
can-fail：把累加换成赋值，必须报出 mismatch —— 实测 **30720/30720** 被抓住。

⚠️ 补这条时我自己的第一版预置值又踩了坑：`((t % 97) - 48.0) * 0.001`
在 `t % 97 == 48` 时正好给出 `0.0`，于是 317 个位置**退化回"清零起始"**、
在那些位置上 `+=` / `=` 又变得不可区分。**判据自己的 premise 检查把它报了出来**
（`non-zero pre-seed = 30403 of E=30720`）。改用 `(t % 97) + 1` 后
can-fail 的捕获数从 30403 升到 **30720**（全覆盖）。

#### (b) 模块头自相矛盾（会主动误导读者）

`b1_pure.rs` 有两段互相冲突的说明：
* 文件头 S1 回退一节：S1 **已回退**，当前是标量；
* 「禁止 8 路归约」一节：写成「**本模块选择采用 S1 的形态**」。

后者是**落地当刻**遗留的措辞，回退时没改。**一个信任错那一节的读者会去重建那个
已知的符号级 bug。** 已改写为：S0 = 当前实现；S1/S2 数字的用途是
**「证明归约禁令有代价」**，S1 的 2.08x 是**尚未兑现的上限**，要拿它必须
**新写一个保符号的乘积内核**并重跑 A1–A5。

#### (c) 删除死代码 `B1_STACK_K`

`pub const B1_STACK_K: usize = 256;` 是回退 S1 时留下的残骸
（它唯一的消费者是被删掉的那个栈缓冲）。全仓库 grep 确认零引用后删除。

#### (d) 一处**假设被证伪**（记录在案）

我原本推断「`b1_backward` 缺少像 `conn_train` 那样的 k0 栈上界硬失败守卫，
应当补上」。**核实后不成立**：B1 的实现里**没有任何栈数组**（grep 栈数组模式 = 0 命中），
所以既没有 0xC0000005 的风险，也没有需要设上界的对象 ——
需要那个守卫的是**已被回退的 S1**（它开了 `[0.0f32; B1_STACK_K]`）。
**结论：不补。** 按原样记录这个推断与它的证伪，避免后人重复。

### 2.5 存储/计算打包（第三轮）：B1 前向向量化 + 缓冲打包

**任务书要求的「把 20 条连接变成稠密小块」。以下逐项对照任务书的四步，并标注
哪几步的**前提被实测修正**。

#### 第一步（确认现状）：实测结论

用 `tools/verify_reference_truth.py` 解析真实产出的 CSR（`L00_ffn.csr`）：

| 问题 | 实测答案 |
|---|---|
| 20 条连接在存储上连续吗？ | **权重连续**：`w[i*k0+j]` 线性布局，每神经元一块 |
| 源 ID 连续吗？ | **不连续**：0/1536 行升序；union = **1536/1536（100%）**；row0 跨 1389/1536 |
| 是 gather 吗？ | **是**，且源不可结构化（见下） |
| B1 前向用 SIMD 吗？ | **完全没用**（`b1_forward` 里 `_mm256` 零命中，纯标量） |

⇒ **慢的根源不是「20 条分散」，是「B1 根本没用向量化」**（1.204 ns/conn，
而向量化的强度行只要 0.167~0.303 ns/conn）。

#### 第二步（存储打包）：**前提被证伪，未做**

任务书设想「源 ID 也连续存储（如果结构化聚类）」。实测：
**union = 1536/1536，即每个源都被某个神经元用到** —— 这是白皮书 §13.6 那条
几何事实的同一面（P18-B §2 已独立测过同样结论）。**任何聚类都改变不了全局
并集**，除非**改变哪些连接存在** —— 而任务书明确禁止改语义。

⇒ **「源 ID 连续」在 k0=20、d=1536、不改语义的前提下不可达。**
权重本来就是连续的（无需打包）；**源侧无结构可打**。

#### 第三步（计算打包）：**做了，且是唯一有效的杠杆**

新增 `kernels::sparse_product_row_avx2`（**保符号**的乘积行，与
`sparse_strength_row_avx2` 并列放置以防再次选错 —— 后者返回 `|w*x|`），
在 `b1_forward` 里**只向量化「取乘积」，归约仍走标量升序单累加器**。

**为什么这样仍 bit-exact**：乘积逐元素独立，`_mm256_mul_ps` 与标量 `*` 逐位
相同；求和顺序一个字节没改。**不用 FMA**（会把两次舍入合成一次，位型不同）。

**缓冲打包**：第一版把 `[0.0f32; 256]` 开在**行循环里面**（每行 1 KB 栈数组）。
实测这是可观开销，已移到循环外只开一次：
```
每行栈缓冲  0.472 ns/conn
共享缓冲    0.303 ns/conn     -> 省 36%
```

#### 第四步（验证）：bit-exact + 性能

**bit-exact（打包前后语义不变）**：
```
vmlm-b1-verify                   checks=20 fail=0
  A1 test_b1_bit_exact           bad=0 / 1536   (f32::to_bits)
  A5 b1_backward bit-exact        bad=0 / 30720
  A5-b 累加语义（预置非零）        bad=0 / 30720
vmlm-lead-b1（独立实现 + A0 oracle 对拍）  oracle vs production = 0/1536
vmlm-b1-canfail（6 种已知错误实现）      checks=7 fail=0（wrong-3 仍抓到 1196/1536）
ci_path_guard                   8 checks / 0 violations / CLEAN
build_all                       All builds OK；引擎体积 74752 B 未变
```

**性能对比（QPC 中位数，3 次独立运行稳定）**：

| | ms/op | ns/conn | ms/step (×15360) |
|---|---|---|---|
| B1 标量（打包前） | 0.0363 | 1.204 | 557.6 |
| **B1 打包（现在）** | **0.0144** | **0.469** | **221.2** |
| 提升 | | | **2.52x** |

#### ⚠️ 目标未达成的如实报告

任务书要求「从慢 5x 变成**接近或快于同参数量稠密**」。**未达成：**

```
同参数量稠密 (d=176)  =  11.5 ms/step
B1 打包               = 221.2 ms/step
=> B1 仍慢 19.2x
```

**而且这个比较是公平的 —— MAC 数几乎相同**（这点修正了我先前的说法）：
```
B1 MACs/matrix/token = d*k0 = 30720
d=176 稠密           = dm^2 = 30976      ratio = 0.99x
```
⇒ 同样的工作量，B1 每 MAC 慢 **16.4x**（0.469 vs 0.0286 ns/MAC）。

**为什么（实测归因，`vmlm-b1-reconcile`）**：
```
products（向量化 gather）  0.303 ns/conn
标量归约（契约要求）        0.234 ns/conn   <- 占 44%，不可去除
缓冲驻留                   0.127 ns/conn   <- 已通过共享缓冲降低
合计（已发布）              0.469 ns/conn
```
* **标量归约占 44% 且不可去除**：bit-exact 契约禁止改求和分组 ——
  8 路 SIMD 归约实测让 **841/1536** 个输出位型分叉（`vmlm-b1-vec` S2）。
* **B1 结构性无数据复用**：每个连接每矩阵只用一次，而稠密 GEMM 的
  packed 内核把 A 行复用 N 次 ⇒ 稠密的每次加载摊薄 ~N 倍。
  **这是 load-bound 的本质，不是打包能解决的。**

**达成的部分是**：B1 打包后比**同结构稠密**（d=1536，829.1 ms/step）快 **3.75x**。
这是诚实的战果 —— 76.8x 的连接减少换来了 3.75x，而不是 76.8x。

#### 顺带修掉的两处自己的缺陷

1. **调和了两个探针 4.5x 的分歧**：bench-builder 报 0.167 ns/conn，
   我报 0.749 ns/conn，都说测的是「打包后的乘积步」。查明：他的探针测的是
   **可被提升的乘积循环**，我的包含**标量归约 + 每行 1 KB 栈缓冲**。
   两者都不错，但**都不是「已发布形态」**。已发布形态 = 0.469 ns/conn。
2. **我的 `b1_packing_position.py` 初版有 1000x 单位错误**（把 ms/op 又乘了
   1000，报出「557568 ms/step」= 每步 9 分钟）。**明显荒谬但格式漂亮**，
   靠与端到端 219 s/step  sanity check 抓出来的，不是重读代码。

### 2.6 SIMD 归约 + u32 索引（第四轮）：验收标准按用户裁决改为 ε 级

**用户裁决**：「B1 直接用 SIMD 归约：`y[i] = SIMD_reduce(Σ w[j]*x[src[j]])`。
验收标准：确定性 ✓、精度 ≤ ε、**不需要 bit-exact**、f32int 直接最优解决。」

#### 交付

| 项 | 内容 |
|---|---|
| SIMD 归约内核 | `kernels::b1_reduce_simd8`（8 路部分和 + **写死**的 8→4→2→1 折叠） |
| 融合内核 | `kernels::b1_dot_row_u32_avx2`（gather + mul + 归约一步完成，`src` 为 u32） |
| u32 索引镜像 | `SparseConnW.src_u32` + `sync_src_u32()` + `assert_src_u32_consistent()` |
| 生产前向 | `b1_forward` → SIMD 路径；标量回退保留 |
| **标量参考** | `b1_forward_scalar_reference`（**保留**，用于算 ε） |
| 几何守卫 | `SparseConnW.assert_geometry()`（新增，见下"崩溃事故"） |

#### 关键设计取舍：用**镜像**而不是改 `src` 的类型

`SparseConnW.src` 是 `*mut f32`，被 `core/` 与 `train/` 下 **92 处**调用点读取。
改类型要重写全部 92 处，而失败形态是**静默的索引错位**（本项目反复对抗的
「看似合理的垃圾数」）。所以**另加 u32 镜像**：

* 爆炸半径为零（既有读取方一行未改）；
* `src` 在生产路径上**只有一处写入**（`init_sparse_conn`），镜像同步点唯一；
* 代价 4 B/连接（120 矩阵共 14.1 MiB，**仅训练工作区**；**磁盘产物不变**，本就是 u32）。

取舍记录：`tools/b1_u32_decision.py`（含被否掉的 3 个方案与理由）。

#### 验收结果（`vmlm-b1-prod-eps`，fail count = 0）

```
[PASS] src/src_u32 镜像一致（30720 项）
[PASS] 精度：worst |a-b| / sum|terms| = 1.229e-07  <= 1e-05
       => 舍入级；比"算错东西"（比值 ~1.0）低 8.1e6 倍
[PASS] 确定性：8 次重复调用位型完全相同

#### ⚠️ ε 判据我写错了两次，两次都是判据的错，不是内核的错

1. **第一次：逐元素相对误差**（`|a-b|/|b|`）→ 报 8.4e-5 "失败"。
   `y` 是 20 个**有符号**项之和，相消时 `|y|→0` 而 `|a-b|` 停在**项**的舍入
   尺度上。这个判据惩罚的是**相消**（数据的属性），不是归约。
2. **第二次：和值的 ulp**（`|a-b| / (eps*|y|)`）→ 报 **706 ulp** "失败"。
   同一根因深一层：最差元素的 `|y_ref| = 1.77e-4`，即和几乎抵消到 0，
   除以它自己的 ulp 会无界膨胀。
3. **正确的判据：与「项幅度之和」比**（`S = Σ|w_j·x_j|`）。
   重排 f32 求和的误差上界是 `k0·eps·S`（此处 2.38e-6·S），而真实缺陷
   （符号/索引/尾块错）会给出 ~S 量级的误差，即比值 ~1.0 —— **差 7 个数量级**。
   实测比值 **1.229e-7**，比一个 f32 epsilon（1.19e-7）还小，**这才是舍入级**。

> 教训：**先看数后选阈值 = 把容差变成橡皮图章**；但更隐蔽的是**选错度量**。
> 两次"失败"都不是内核的问题。判据本身也会错，而且错了会看起来像内核错。

#### 旧 bit-exact 判据已**降级为参考**（未删除）

按用户要求，`A1 test_b1_bit_exact` 与 `-0.0` 保序判据改为**参考**，
仍打印位差计数（实测 **844/1536**，45.1% 位型相同）+ 量级比值，
便于发现"偏离变大"，但不再作为阻塞项。

**同时如实记录被放弃的契约**：
* `-0.0` 保序（`neg_zero` 从 4 变 0）—— SIMD 从零向量起步，`0.0+(-0.0)=+0.0`；
* 严格升序单累加器 —— 8 路部分和按定义违反。
保留一条 `A1-ref` 判据证明**标量首项赋值形态确实能保住 `-0.0`**（4/4），

#### 🔴 顺带修掉一个真实的崩溃事故（我自己引入的）

改 SIMD 后 `vmlm-b1-canfail` **0xC0000005 崩溃、无任何诊断**。根因：
该探针的 `wrong-5` 用 `SparseConnW { k0: k0+1, ..sc }` 做"错行宽"对照 ——
`k0` 与缓冲区不符。旧标量版一次读一个 f32，"越界一格仍落在分配余量里"所以
**侥幸活下来**；新内核按 k0 以 **8 宽**读 `src_u32`，最后一行越过末尾 32 字节，
而 `src_u32` 位于分配区**最后一块** ⇒ 直接访问违例。

**"旧代码活下来了"不是正确性证明。** 两处修复：
1. **生产侧**：新增 `assert_geometry()`（`e == n_neurons*k0`），把静默崩溃
   换成可读报错 `CONN_TRAIN: SparseConnW geometry inconsistent: e=... but n_neurons*k0=...` + exit 9；
2. **探针侧**：4 处 `k0±1` 的非法构造改为**几何自洽**的窄/宽结构 ——
   这样测的是"漏算一条 / 错行宽"这个**想法**，而不是未定义行为。

顺带修掉一处**判据混杂**：`wrong-6`（操作数交换）原以 `y_ref`（现在是 SIMD）
为基准，把"交换"与"归约顺序"两个效应混在一起报出 844 位差。改为与**标量契约参考**
比较后恢复为 0 —— 与"乘法交换律不可观测"这个结论一一对应。

#### 同结构稠密（d=1536，4 投影 qkv+wo × 24 层）

```
同结构稠密        872.4 ms/step   (9.0875 ms / 矩阵)
B1 shipped         89.1 ms/step   (0.7425 ms / 矩阵)
────────────────────────────────────────────────
B1 比同结构稠密快  12.24x（每矩阵同口径）

#### 同参数量稠密（d=176，4 投影 × 24 层）

```
同参数量稠密       10.1 ms/step    (0.1052 ms / 矩阵)
B1 shipped         89.1 ms/step    (0.7425 ms / 矩阵)
────────────────────────────────────────────────
B1 反而慢          7.1x（每矩阵同口径）

**这个比较是公平的，不是口径问题**：
```
B1 MACs/matrix/token = d*k0 = 30720
d=176 稠密 MACs      = dm^2 = 30976
比值 = 0.99x  <= 同样的工作量
```
每 MAC：B1 **0.1888 ns/MAC** vs 稠密 AVX2 **0.0265 ns/MAC** ⇒ **稠密高 7.1x**。
（自检：0.1888 ns/MAC 与直接实测的 0.189 ns/conn 一致。）

**结构性原因**：稠密 packed 内核把一次加载的 A 行在 N 维上复用；
B1 的 30720 条连接**每条每矩阵只用一次**，无复用可摊薄。

#### 本次优化自身的倍速

```
B1 标量参考（bit-exact 契约版）  583.7 ms/step   0.0380 ms/call   1.237 ns/conn
B1 shipped（SIMD 归约 + u32）     89.1 ms/step   0.0058 ms/call   0.189 ns/conn
────────────────────────────────────────────────────────────────
提升                              6.55x
```
（vs 算子版 `sparse_forward(k=8)`：`vmlm-b1-verify` 报 **37.3x**。）

#### ⚠️ 本轮我自己又犯了两次单位错误（都记录）

1. **把整步时间当成单层**：算出「B1 每矩阵 17.82 ms」，而 89.1 ms 是
   **全部 24 层 120 个矩阵**的和 ⇒ 正确值是 0.7425 ms/矩阵。错了 **24x**。
   被 `0.189 ns/conn × 30720 = 0.0058 ms/call` 与 `89.1/15360 = 0.0058` 的
   **互检**抓出来 —— 两个独立算法给出同一个数，第三个（我的）对不上。
2. **per-MAC 漏乘 128 token**：一层每 token 做 `d*k0` 次 MAC，而一层有 128 个
   token，所以每个矩阵是 `30720*128` 次 MAC。只除 `d*k0` 会错 **128x**
   （报出 24.17 ns/MAC 而非 0.1888）。同样是自检抓出来的。

> 两次都是**同一个量用三种方式表达时对不上**。这比"算错一个数"更值得留档：
> **对数量级敏感的结果，应当用至少两条独立路径互算，再比对。**

## 5. 🔴 重大事故：S1 落地引入符号级 bug（已回退）

**这是本轮最重要的记录**：一个被探针判为「bit-exact 可落地」的优化，
落地后是**错的**。

### 5.1 经过
1. bench-builder 提议 S1（向量化取乘积 + 标量顺序累加），自建复刻内核实测

3. **落地后 A1 判据立刻报 `bad = 1536/1536`。**
4. Lead 独立诊断（`train/src/lead_b1_s1diag.rs`，`vmlm-b1-s1diag`）：
```
kernel=+0.005257437  scalar=-0.005257437   |equal|=true
值不匹配 = 15314 / 30720，其中【纯符号翻转】= 15314  (100%)
VERDICT: the kernel returns |w*x|. It is the STRENGTH kernel.
端到端 b1_forward vs 算子参考 = 1536/1536 分叉

5. **b2-builder 独立发现同一 bug**（证据链不同：逐行比对 8 行，确认

绝对值是它的**语义**。拿它当**乘积**会摧毁每个负项的符号。

## 6. 76.8x 的真相（本轮最重要的量化）

### 6.1 两个基准都报（用户要求）

| 基准 | d | ms/step | 性质 |
|---|---|---|---|
| **同结构稠密** | 1536 | **840.6 ~ 860.7** | 实测（AVX2 `gemm_nt`，min-of-reps） |
| **同参数量稠密** | **176** | **10.1** | **实测** |

同参数量口径：`sqrt(d*k0) = sqrt(1536*20) = 175.3` ⇒ d≈176。

### 6.2 ⚠️ 口径更正（作废了两个数字）

**初版用了「7582.1 ms/step」当同结构稠密基线 —— 那是标量循环，不是 AVX2。**
bench-builder 发现、Lead 复跑确认。`profile_probe.rs:167-185`（qkv）与
`:211-221`（Wo）是**手写标量三重循环**；只有 A/B 段（`:368`/`:386`）调 `gemm_nt`。
同一次运行的两个口径：
```
qkv 163.740 ms/call, Wo 155.221 ms/call        <- 标量
one [128x1536]x[1536x1536]: scalar 155.32  gemm_nt 13.21  speedup 11.76x
extrapolated = 14910.4 ms/step scalar vs 1267.9 ms/step AVX2
```
⇒ **「98.7 ms/step 理论值」与「37.5x 差距」两个数字作废**（已在 AUDIT §5.1 标注）。

### 6.3 76.8x 是**算术量**的比值，而稠密侧自己就能兑现它

- 算术量比值 **76.8x** 复核成立（30720 vs 2359296 连接）。
- 但 d 从 1536 → 176（MACs 降为 **1/76.2**），实测加速 **85.2x**（**超线性**）。
⇒ **76.8x 兑现不了不能归因于算术量本身。**

### 6.4 真正的归因

```
B1   = 534.5 ms/step  (14.19x vs 同结构稠密 7582.1 标量口径)
B2 SHARED = 795.6 ms/step  ( 9.53x)
B2 PER-ROW = 6076.4 ms/step ( 1.25x)  <-- 几乎不比稠密快
```
1. **选择次数是关键，不是选择实现**：per-row 做 `d × k0 × k` 次比较
   （245760 上界 / 77965 实测），**与连接数减少完全无关**。
   它省了 76.8x 乘加，却在**每个神经元**上做一次选择 ⇒ 全部收益被吃掉。
2. **即便选择归零（SHARED），也只到 9.53x** —— 剩余差距在强度行（含 gather）。
3. **B1（无选择）也只 14.19x** —— 剩余在 gather 与标量累加。
4. **转译化改不了以上任何一项**（整层口径还净亏 1955 ms/step）。

### 6.5 B1 剩余 gap 的布局分析（`vmlm-lead-b1-gap`）

同一批 30720 次乘加，四种数据布局：
```
L1 src=随机 f32 (现状)   0.0364 ms  1.20 ns/conn
L2 src=随机 u32          0.0093 ms  0.30 ns/conn
L3 src=排序 u32          0.0094 ms  0.31 ns/conn
L4 稠密无 gather         0.0080 ms  0.26 ns/conn   <- 布局天花板
```
**⚠️ 但这是标量口径，不可外推。** bench-builder 用复刻的**向量化**路径实测：
```
向量化下 u32 src 收益 = 0.95x / 1.45x / 0.98x  (3 次独立进程，符号会翻)
k0=64 reps=5000       = 1.10x / 0.96x / 1.08x  → 约 1.0-1.1x
```
机制：8 宽 `vcvttps2dq` 走独立端口，被 gather 延迟掩盖；
标量 `cvttss2si` 串在依赖链上无处可藏。**两种口径都对，不能跨用。**
⇒ **u32 src 建议已撤回**（生产路径 `compute_act_mask` 已是向量口径）。

## 11. 本轮的方法论产出（比结论更可复用）

**四条假数字/假绿灯，全部是本会话真实踩到的**：

1. **假零（自己）**：`b1_forward = 0.0000 ms`，因为写出的 y 没人读，循环被删。
   修法：`consume()` 强制读回 + **下界断言 <1e-4 ms 就 FATAL 退出**。
2. **假零（bench-builder）**：S3 报 0.00000 ms，因输入输出在 reps 循环里
   全是不变量被整段提出；**更糟的是他的 `[FATAL]` 守卫只 `println`，
   那个 0 照样流进表里**。⇒ **守卫必须能中断输出，不能只打印。**
   他还发现：S0/S1/S2 逃过提升**只因为它们经 gather 读内存** ——
   **「正常数字」不等于「探针有效」**。
3. **测副本而非被测代码（Lead + trans-builder）**：Lead 的探针自带一份
   `b1_forward`；trans-builder 原始判据也只测自己的复刻。
   ⇒ 已固化 **A0 判据**（oracle vs production 逐位对拍）与 **[2b]**。
4. **跨口径外推（Lead，三次）**：标量→向量、取值→取值+累加、
   单算子→端到端。每次都被 bench-builder 抓出来。
   ⇒ **口径必须随数字一起报告。**

**一条通用结论**：本轮三个最关键的技术纠错（7582.1 是标量、u32 不可外推、
向量化只值 2.05x）**全部来自把数字与"另一个测量基"对拍，而不是重读同一个探针**。
