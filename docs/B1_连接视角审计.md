## 1. 五个审计问题（逐条实测）

### Q1：权重 `w[0..20]` 在内存里连续吗？

**答：连续，且无填充。**（解析真实产物 `artifacts/p18_sparse24/L00_ffn.csr`）

```
w 数组在文件内的起点     = 129048
神经元的 20 个权重占据   = [129048 + i*20*4, ...) 即 80 字节连续块
逐行间隙检测             = 0 处（0 => 完全紧凑、无 padding）
```
⇒ **权重侧无需打包**。`w[i*k0+j]` 本来就是一块 80 字节的线性数组。
（这一条**在上一轮打包之前就已成立**，不是打包的成果。）

### Q2：源 ID `src[0..20]` 连续吗？

**答：`src` 数组本身连续（连续读取），但它的**取值**完全无序。**

```
0/1536 行是升序
相邻对下降（delta < 0）= 14550 / 29184 = 49.9%
```
⇒ 读 `src` 是顺序访问（无额外开销）；**用** `src` 是随机访问。
这两件事必须分开说 —— 混起来就会得出"读 src 有开销"的错误结论。

### Q3：`x[src[j]]` 的访问模式 —— 随机还是聚类？

**答：完全随机，且没有可挖掘的结构。**

```
每个神经元 20 个源的跨度(max-min)：min 781  median 1409  mean 1390.4  max 1534
  平均跨度覆盖源空间的 90.5%
每行触及的 64 字节缓存行数：min 14  mean 18.1  max 20   (理论最优 = 2)
全体源的并集 = 1536 / 1536 = 100.0%
```
⇒ 并集是**全集** —— 这是白皮书 §13.6 那条几何事实（P18-B §2 独立测过同样结论）。
**任何聚类都改变不了全局并集**，除非改变"哪些连接存在"（= 改语义）。

### Q4：与纯 d=20 稠密点积对比

**答：B1 是纯稠密点积的 5.0x（标量）/ 3.15x（含向量化）。**

四个变体，同样 30720 次乘加（`vmlm-b1-dot20` 与 `vmlm-b1-scatter` 独立互证）：

| 变体 | ns/conn | vs 稠密 |
|---|---|---|
| S4 无 `src` 数组（纯 d=20 稠密点积） | **0.238** | 1.00x |
| S1/S2 有 `src` 数组，但源**顺序** | 1.185 | 4.98x |
| S3 有 `src` 数组，源**真随机**（现状） | **1.195** | 5.02x |

⇒ 关键读数：**S2（顺序）与 S3（随机）几乎相同（1.185 vs 1.195）**。
**散射只值 0.010 ns/conn。** 而"有 `src` 数组"这件事本身值 **0.947 ns/conn**。

### Q5：有没有非计算开销？

**答：已经基本清空。** 逐条核对**真实源码**（不是关键词扫描）：

| 项目 | B1 中存在？ |
|---|---|
| 算子分发 / 间接调用 | ❌ 无 |
| 掩码 `act[]` 读写 | ❌ 无（A2 判据实测前向期间写 0 次） |
| 槽位读写（解释器状态） | ❌ 无 |
| top-k 选择 | ❌ 无 |
| gather 式跳过分支 | ❌ 无 |
| 每行 1 KB 栈缓冲 | ⚠️ **有**（上一轮已移到循环外） |
| 每行一次内核调用 | ⚠️ **有**（唯一剩余项） |

⇒「掩码占前向 103%」属于 **B2/算子路径**，与 B1 无关。
B1 剩下的非计算开销只有**每行一次内核调用**（已在 `vmlm-b1-reconcile` 量过）。

## 2. 🔴 核心更正：成本构成与"索引映射"的直觉相反

任务书说：

> 「索引映射表的作用：把 1536 维空间里的 20 个位置映射到 20 维紧凑空间」
> 方向 1：「让 x[src[j]] 访问局部化 —— **这是唯一和"稀疏"有关的优化方向**」

**实测：这是错的。** 差距的 99% 不在"映射到哪"，而在"取索引"这个动作本身：

```
S4 无 src 数组（纯稠密 d=20）        0.238 ns/conn
S3 有 src 数组 + 真随机散射（现状）   1.195 ns/conn
────────────────────────────────────────────────
   差 0.957 ns/conn，拆开：
     索引加载 + f32→int 转换   0.947 ns/conn   = 99.0%
     散射（缓存行为）          0.010 ns/conn   =  1.0%
```

**为什么散射几乎免费**（这是可解释的，不是巧合）：
```
x 数组 = 1536 floats = 6144 字节 = 6.0 KB
L1d 数据缓存（i3-12100F）      = 48 KB
```
⇒ **整个 x 向量常驻 L1**。20 次 gather 每次都命中 L1（4 周期延迟），
所以"随机 vs 顺序"在 L1 内几乎没有区别 —— **没有 cache miss 可以避免**。

**⇒ 方向 1（聚类）无效，因为它优化的正是那个只值 1% 的东西。**

## 3. 真正的成本：索引的 `f32→int` 转换

拆解索引成本（`vmlm-b1-indexcost`，标量口径）：

| 变体 | ns/conn | 差值 |
|---|---|---|
| `src` 为 f32（现状：加载 + `cvttss2si`） | 1.185 | — |
| `src` 为 u32（只加载，无转换） | **0.309** | **−0.876** |
| 纯稠密 d=20（无索引） | 0.238 | −0.947 |

⇒ **转换值 0.876，索引加载只值 0.072。**
即：`src` 存成 `f32` 这件事，占了 B1-vs-稠密差距的 **92%**。

**机制**（为什么标量下它这么贵）：
```
每条连接：
  1. load src[j]      (4B, 连续, L1)       <- 便宜
  2. cvttss2si        float -> int          <- 贵
  3. load x[sid]      (gather, L1 命中)     <- 便宜
```
第 2 步**坐在地址依赖链上**（gather 的地址要等它），无法与 gather 重叠。
0.876 ns ≈ 3 个周期/连接（@3.5GHz）。

### 3.1 ⚠️ 跨口径陷阱：两个数都"对"，但只有一个是发布形态

`u32 src` 的收益在两个口径下完全不同：

| 口径 | 收益 | 谁在测量 |
|---|---|---|
| **标量循环** | **3.8x** | 本次 `vmlm-b1-indexcost` |
| **纯向量乘积**（无归约） | **1.05x** | bench-builder `vmlm-vec-gather` |
| **已发布形态**（向量乘积 + 标量归约） | **1.43x** | 本次 `vmlm-b1-shipped-u32`（决定性） |

**为什么差这么多**：向量路径下 `cvttps2dq` 一次转 8 个索引、走独立端口，
**被 gather 延迟掩盖**；标量路径下 `cvttss2si` 一条一条、暴露在依赖链上。

**我特别标出这一条，因为我在本会话已经因跨口径外推错过一次**
（AUDIT §5.2：我把标量 4x 外推到向量路径，被 bench-builder 证伪）。
所以本次**没有外推，直接测了发布形态**：

```
vmlm-b1-shipped-u32（已发布形态：向量乘积行 + 标量归约）
  f32 src   0.534 ns/conn   0.0164 ms/op
  u32 src   0.374 ns/conn   0.0115 ms/op
  speedup   1.43x           输出 bit mismatches = 0 / 1536
  身份一致性 f32/u32 = 0/30720（往返无损）
```
⇒ **u32 src 在发布形态上值 1.43x，且 bit-exact。**
（磁盘格式 `CS_SRC_ENTRY=4` 本来就是 u32；训练侧工作区存成 f32 是纯往返转换。）

## 5. 要到理论值附近，还差什么（可执行的唯一路径）

按实测排序，**剩余空间只有两项**：

```
已发布形态 = 0.53 ns/conn（本次实测，vmlm-b1-shipped-u32）
  其中：  索引转换 f32→int     ~0.16 ns/conn   <- 可消除（改 u32）
          标量归约              ~0.23 ns/conn   <- bit-exact 契约要求，不可消除
          向量乘积 + 其余        ~0.14 ns/conn
  纯稠密 d=20 地板              0.238 ns/conn
```

1. **`src` 改 u32 → 1.43x（实测，bit-exact 0 分叉）** —— 唯一的低风险收益。
2. **标量归约占 44% 且不可去除** —— 8 路 SIMD 归约实测让 **841/1536** 输出分叉
   （`vmlm-b1-vec` S2）；要拿它必须放弃 A1 判据。

⇒ **即便把索引转换清零，B1 也到不了纯稠密 d=20 的地板（0.238）**，
因为标量归约本身就在那之上。**这是 bit-exact 硬约束的代价，不是实现不足。**

## 6. 本次审计中我自己的两次测量错误（都记录）

1. **Q4 初版的"连续"变体不公平**：它读 20 float 小数组，
   与"随机"变体的 1536 float 大数组差的是**数组大小**，不只是散射。
   于是报出"散射 0.007 ns/conn"这种反直觉数。
   ⇒ 写了 `vmlm-b1-scatter` 把两者彻底分开，确认结论（散射 ≈ 1%）**成立**，
   但初版的**归因是错的**。

2. **`vmlm-b1-scatter` 的 S1 初版自带一个 `% k0`**：整数取模是除法，
   每条连接执行一次，**测出来比大数组还慢（1.702 vs 1.185）**。
   这是"探针本身比被测对象还贵"的又一例。
   ⇒ 把取模移到计时之外，S1 降到 1.185，数据自洽。

3. **顺带记录**：`vmlm-lead-b1-u32src`（上一轮的探针）里的
   `b1_f32_src` / `b1_u32_src` 是**本地标量函数、不是发布路径**。
   它报的 3.87x 是**标量口径**，不能当作发布形态的结果 ——
   这正是我这次要单独写 `vmlm-b1-shipped-u32` 的原因。

## 7. 边界（不许淡化）

1. **本次未改任何生产代码**（任务要求）。u32 src 只是**测出来值 1.43x**，
   **尚未落地** —— 落地需要改 `SparseConnW.src` 类型，是一次生产变更，
   必须重跑 A1–A5 全套。
2. **机器漂移**：本机 ms 级数字只宜作量级参考（d=1536 跨度约 9%）。
3. **S1/S2/S3 的对比用的是标量循环**（为了与"纯稠密点积"同口径）。
   已发布的向量化形态单独测了（§3.1），两者不可混用。
4. **`x` 全在 L1 是 d=1536 特定形状的结论**。d 更大时 x 超出 L1，
   散射的权重会上升 —— **该结论不外推到其他 d**。
