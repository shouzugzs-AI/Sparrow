# VMLM 无差别逐条优化报告（P19）

本报告只记录**实测**：每条改动 → 改完跑 50–100 步 → 记录「每步耗时 / loss 曲线 / NaN / 崩溃」→
快就保留、慢就回退、不确定就保留并写明。不设收益门槛，也没有"看起来没用就不做"的筛除。

* 迭代基准：`dim 2048 / k0 8 / k0-embed 16 / k0-head 16 / k0-attn 4 / layers 12 / attn-every 4 /
  seq 64 / batch 16 / threads 8 / inter / persistent-threads / pin / attn-window 1 / head-skip 1 /
  data = artifacts\zh_wiki(vocab 8198) / 100 步`
* 生产基准：`dim 4096 / layers 32 / attn-every 8 / batch 32 / 其余同上 / 12 步`
* 计时口径：`train_log.csv` 的 `elapsed_s`（原为 `{:.1}`，1 位小数无法分辨 <5% 的改动 ⇒ 先改成 `{:.4}`），
  取「第 10 步之后每步增量的中位数」；同时报 min。测试机是 4 核 8 线程，8 worker 会互相抢核，
  再叠加开发环境的背景负载 ⇒ 同版本重复测量的离散度约 ±8%（同一份二进制复测出现过 0.149 / 0.165 / 0.173）。
  **结论用的都是同一时段、同一脚本的前后对比**，并且用两个配置交叉验证。

## 0. 总账

| 配置 | 优化前（pristine 重建实测） | 优化后 | 倍数 |
|---|---|---|---|
| 迭代基准 100 步 | 0.437 s/步（中位）/ 43.9 s 循环 | **0.149–0.173 s/步**（中位）/ 16.3–17.5 s | **2.6–2.9×** |
| 生产基准 12 步 | 2.56 s/步 | **1.21–1.28 s/步** | **≈2.0–2.1×** |

* 两个配置都：loss 单调下降（迭代 9.0123→9.0035 / 生产 9.0123→9.0117），**0 次 NaN、0 次 0xC0000005**。
* 回归：`--gradcheck 1`（稀疏 IO + 注意力 + head-skip）**PASS 60 探针/越界 0**；稠密 IO **PASS 45 探针/越界 0**；
  `vmlm-b1-verify` 20/20、`vmlm-b1-canfail` 7/7、`vmlm-b1-prod-eps` ALL PASS、`vmlm-bwd-check` PASS。
* 生产尺寸 4096×32×batch32 与迭代尺寸的**瓶颈结构不同**（生产是「逐层反向 61.5% / 前向 32.8%」，
  head 只剩 5.2%），所以两个倍数不一样是真实的，不是测量口径差异。

## 1. 逐条改动（按实现顺序）

### P19-0 计时精度（仪表，非优化）
`train/src/b1_full_train.rs`：`train_log.csv` 的 `elapsed_s` 由 `{:.1}` → `{:.4}`、`tok_per_s` `{:.1}`→`{:.2}`。
原行为：0.44 s/步只能看到 0.4/0.5；新行为：可见 4 位小数。**无性能影响**，但后面所有 1–3% 的判定都靠它。

### P19-1 attention 前向核心向量化（保留）
* 位置：`core/src/kernels.rs`（新增 `dot256_f32` / `axpy256_f32` / `axpy2_256_f32` / `add256_f32` /
  `max256_f32` / `exp_neg_sum_avx2` / `scale_mul_avx2` / `sum256_f32` 原语）；
  `train/src/b1_full_train.rs::attn_core_row`。
* 原行为：q·k 是**单累加器串行链**（每元素 4 周期延迟、零 ILP）；概率加权和 `o[x] += a·v[x]` 是裸指针
  标量循环（无 noalias ⇒ LLVM 不向量化）；`o` 归零是标量循环。
* 新行为：点积走 4 链 FMA + 横向归约；加权和走 8 宽 `axpy`；归零走 `write_bytes`。
* 实测：**0.4423/0.4318 → 0.3773 s/步（−14.7%）**；相位「嵌入+逐层前向」39.94→30.49 s、
  「逐层反向」238.7→199.2 s（反向里也含一次 attention 重算）。

### P19-2 attention 反向三趟向量化（保留）
* 位置：`attn_core_bwd` / `attn_core_bwd_par`（passA 点积、passB `axpy2`、passC `axpy`、`write_bytes`）。
* 实测：0.3773 → **0.3735（−1.0%）**，相位 4 199.2→196.8 s。
  收益远小于预期 ⇒ 说明当时相位 4 的大头不是这三个 pass（后面 P19-3 证实是线程风暴）。
  仍保留（方向正确、无副作用）。

### P19-3 修「嵌套线程风暴」调用点（保留，单项最大收益）
* 位置：`b1_full_train.rs` 反向注意力调用点，`attn_backward_sparse_par(..., nth, dwp)` → `nt_in`。
* 原行为：inter 模式下 `step_fn` 本身已经跑在 8 个 pool worker 上，内层又按 `nth=8` spawn 一层
  ⇒ **每步 3 个 attention 层 × 8 个 region = 24 次「8 线程 spawn + 3 次 barrier」，4 物理核上跑 64 个线程**。
* 新行为：内层并行度 = 本 region 的**体内**并行度（inter 下为 1，即串行；intra 下等于 nth，逐位不变）。
* 实测：**0.3735 → 0.1997 s/步（−46.5%）**；相位 4 79.6 s。这条把「单内核微基准 0.59 ns/conn 而相位耗
  却是它的 6 倍」的矛盾解释掉了。

### P19-4 attention 状态缓存，去掉反向重算（保留）
* 位置：`b1_full_train.rs`（`aq/ak/av/ao/asp` 由每 region 一份 → **每 attention 块一份**，窗口 w 的数据
  落在块内偏移 `(n_win−1−w)`；反向删掉 `b1_forward` 整层重算 + `attn_forward_sparse` 5 个投影重算）。
* 原行为：每个 attention 块的反向要先重跑 **1 次整层稀疏前向 + 5 次稀疏投影前向**（共 6 次）。
* 新行为：前向把 `asp` 与逐窗口 q/k/v/o/prob 缓存下来，反向直接用。
* 实测：**0.1997 → 0.1797（−10.0%）**；相位 4 79.6→62.0 s；代价是前向多一次 `[tt×dim]` 拷贝。
* 内存：`aq/ak/av/ao/asp` × `n_attn`，生产配置约 +0.5 GB（机器 15.8 GB，实测跑满 12 步无 OOM）。
* **语义副作用（必须知道）**：块首现在是「最后一个窗口」这一条被刻意保留（标定/体检读基址的语义不变），
  但**标定本身**过去是「三个块都读同一份 scratch（= 最后一块的 q/k）」，现在**每块读自己的**。
  于是 `g` 由 274.082 → 270.250（+1.4%），逐块输入 RMS 也不再相同。这是一处**潜在 bug 的修正**，
  但它改变了训练数值（100 步 loss 轨迹仍在 1e-6 内，因为 softmax 近似均匀、g 影响极小）。

### P19-5 `b1_forward` 小 k0 打包路径（保留）
* 位置：`core/src/kernels.rs::b1_forward_packed_avx2` + `core/src/b1_pure.rs::b1_forward` 分发。
* 原行为：k0<8 时 `while j+8<=k0` 一次都不成立 ⇒ 整行落标量尾部循环，行开销（调用/累加链/横向归约）
  占满；实测 k0=4 是 **0.4754 ns/conn**，而 k0=8 只要 0.1896。
* 新行为：G = 8/k0 个**连续行**塞进一个 ymm（k0=4 → 2 行/ymm，k0=2 → 4 行，k0=1 → 8 行，k0=8 → 1 行），
  一次 gather + 一次连续 w/src 载入覆盖 G 行；k0=8 顺便把 4 步归约折成 2 步。
* 实测（`core/examples/kbench --mode smallk`，n=2048, t=128）：k0=4 **0.4754→0.2150 ns/conn（2.21×）**；
  k0=8 **0.1896→0.1596（1.19×，且与发布版逐位相同 max|diff|=0）**。
* 端到端：0.1797 → **0.1741（−3.1%）**。

### P19-6 CE/softmax 三个标量 pass 向量化（保留）
* 位置：`b1_full_train.rs` CE 段（`max256_f32` / `exp_neg_sum_avx2` / `scale_mul_avx2`），
  `kernels.rs::exp_neg_ps_avx2`（与标量 `exp_f` 同系数、FMA Horner、半开区间口径）走新增的 `exp_neg_sum_avx2`。
* 原行为：每个 position 3 × 8198 次标量访问，其中 `exp_f` 是 15 条标量指令。
* 实测：**0.1741 → 0.1694（−2.7%）**；相位 CE 7.475→2.368 s（**−68%**）。

### P19-7 块对齐 head 反向（保留）
* 位置：`kernels.rs::head_block_bwd_avx2`、`b1_full_train.rs::par_head_bwd` + 拓扑**实测校验**
  （`src[v][j] == (v%nb)*k0_embed + j` 对全部 v,j 校验一遍，且要求 `!dyn_sub && head_hot_pool==0 &&
  nb 是 2 的幂 && k0_head<=k0_embed && HAS_AVX2`，不满足整条退回通用内核）。
* 原行为：head 反向走通用 fused 内核（gather + 标量散写）。
* 新行为：源连续 ⇒ 每行 2 个 16 float 连续 FMA（`dw[v][·] += dy[v]·h_b`、`dh[b·] += dy[v]·w[v][·]`），
  无 gather、无标量散写、**不需要任何数据重排**（`dw` 仍是 `head_dw` 的行主序、`dh` 仍是 h 的自然布局）。
* 实测（kbench）：8.39→3.97 ms/round(128 token)（**2.1×**）；端到端 **0.1694 → 0.1513（−10.7%）**，
  head 反向 14.80→8.06 s、「嵌入反向」（含 head2 反向）13.99→7.52 s。

### P19-8 head 前向 WT（列主序权重）路径（保留，含一处必须的修复）
* 位置：`kernels.rs::head_pack_wt_avx2` / `head_pack_ht_avx2` / `head_block_fwd_wt_avx2`；
  `b1_full_train.rs::par_head_fwd_wt` + 每步 Adam 之后重打包。
* 原行为：通用 gather 前向（2 次 gather + 8 路归约/行）。
* 新行为：W 预先转置成 `WT[j*nv+v]`，**8 个连续行（= 8 个相邻块）放一个 ymm 通道**，按 j 累加 ⇒
  无 gather、无横向归约；h 侧只需一次 `k0h×nb` 的小转置（2 KB、L1 常驻）。
* 实测（kbench，n_vocab=8198）：通用 2.555 ms → **WT 1.174 ms（2.18×）**；
  而「行主序、无 WT」的两个变体是 **0.89× / 0.95×（更慢）**，已否决（见 §2）。
* 端到端：0.1513 → **0.1495（−1.2%）**，head 前向 10.264→7.787 s（−24%）。
* **必须的修复**：WT 是 head.w 的副本 ⇒ 任何改 head.w 的地方之后都要重打包。`--gradcheck 1` 的
  中心差分直接扰动 `head.w`，第一版没重打包 ⇒ **head 组 6 个探针 FD 恒为 0、GRADCHECK FAIL**。
  已加 `repack_head_wt(...)` 于：检查点载入后、Adam 之后、FD 的每次扰动后。修后 **PASS 60/0**。

### P19-9 Adam / clip_grad / inter-slot 归约向量化（保留）
* 位置：`kernels.rs::adam_avx2`（8 宽，`sqrt_ps` + `div_ps`）、`train.rs::clip_grad`（`dot256_f32`
  + `scale_mul_avx2`）、`b1_full_train.rs` 的 `red()`（`add256_f32`）。
* 实测：0.1495 → **0.1489（−0.4%）**。收益很小，但方向正确、逐元素口径只差 ε，保留。

## 2. 实测后**否决**的条目（都留了数据，不"看起来没用"就跳过）

| 条目 | 做法 | 实测 | 结论 |
|---|---|---|---|
| t8 令牌分块前向 | `b1_transpose_activations` + `b1_forward_t8`（含转置成本） | k0=8 **0.48×**、k0=4 **0.62×**（0.189→0.397 / 0.476→0.763 ns/conn） | 否决：转置开销 > gather 省下的 |
| B1 fused 反向 V2 | 用 `vpextrd` 取通道，去掉 `sid` 存栈再标量读回 | 1.01×（0.6023→0.5975 ns/conn） | 否决：无收益 |
| B1 fused 反向 V3 | 2 行并行（两条独立 gather/散写链） | **0.95×**（更慢） | 否决 |
| head 行主序前向 | 不转置、块主序/行主序两种遍历 | 0.89× / 0.95× | 否决（P19-8 的 WT 版才是 2.18×） |
| head j-主序 dWT 反向 | 外积式 `dWT[j][v]` | 1.70× | 否决（行主序版 2.1× 更好） |
| B1 反向"零散写"改造 | 源主序 + 静态逆索引表 | 估算 2 gather/源 ≈ 10 cycle/源，与现状相当 | 未实现（推算不划算，留档） |

## 3. 可复现性 / 确定性影响（按用户裁决：默认保留，逐条列出量级）

1. **不再逐位相等**（FMA 把乘加融成一次舍入、8 路归约改变分组）的路径：
   attention core 前/反向、CE/softmax、head 前向、`b1_forward` 的 k0<8 分支、
   `clip_grad`/`adam`/`red`。单条改动量级 ≈ 1e-7 相对；端到端 100 步 loss 轨迹变化 **≤1e-6**
   （迭代基准 pristine 9.01233→9.00347 与现在 9.01232→9.00347，同到 6 位小数）。
2. **`b1_forward` 的 k0=8 分支逐位不变**（kbench 报 max|diff| = 0），k0=20 等非 {1,2,4,8} 的 k0
   完全走原路径 ⇒ `vmlm-b1-verify` 20/20、`vmlm-b1-canfail` 7/7、`vmlm-b1-prod-eps` 全 PASS 仍成立。
3. **P19-4 改变了标定输入**（每块读自己的 q/k，而不是都读最后一块的 scratch）：
   `g` 274.082→270.250（+1.4%），这会让"从 pristine 权重继续训练"与"本次从头训练"的轨迹**不可逐位对齐**。
   这是修正而非退化，倾向保留。
4. **`--threads 1` 不再等于历史逐位结果**（同上）；`--threads N` 内部仍按 slot 升序固定归约。
5. 新增长期缓冲：`aq/ak/av/ao/asp` 由 1 份变 `n_attn` 份（生产配置 +≈0.5 GB），
   `head_wt/head2_wt` 各 `nv*k0_head`（≈0.5 MB × 2），`head_ht` 每 token 一份（≈33 MB 生产配置）。

## 4. 复现方式（新增的脚手架都在 `_opt/` 与 `core/examples/`，不是交付二进制的一部分）

```powershell
# 内核微基准（不改 trainer，直接给 ns/conn）
cargo build --release -p vmlm-core --example kbench --features train,conn-sparse
.\target\release\examples\kbench.exe --mode all --dim 2048 --k0 8 --t 128          # 层前向/反向
.\target\release\examples\kbench.exe --mode headall --dim 2048 --t 128            # head 前向4版/反向3版
.\target\release\examples\kbench.exe --mode smallk --dim 2048 --k0 4 --t 128      # 小 k0 打包
.\target\release\examples\kbench.exe --mode bwdvar --dim 2048 --k0 8 --t 128      # 反向变体
.\target\release\examples\kbench.exe --mode t8     --dim 2048 --k0 8 --t 128      # t8 否决依据

# 端到端（_opt\bench.ps1 会跑完并汇总 s/步 + loss + NaN/崩溃）
powershell -NoProfile -ExecutionPolicy Bypass -File _opt\bench.ps1 -Tag x -Steps 100 -Profile 1
powershell -NoProfile -ExecutionPolicy Bypass -File _opt\bench.ps1 -Tag x -Config full -Batch 32 -Steps 12 -Profile 1

# 数值梯度自检（本文档最重要的正确性判据）
.\target\release\vmlm-b1-full.exe --sparse-io 1 --dim 64 --k0 4 --k0-embed 16 --k0-head 16 --k0-attn 4 `
  --layers 4 --no-residual 1 --head-skip 1 --attn-every 2 --attn-sparse 1 --attn-src-shared 1 --attn-calib 1 `
  --attn-window 1 --seq 16 --batch 2 --steps 1 --data-dir artifacts\b1_scaling --threads 1 --gradcheck 1
```

* 原始源码备份：`_opt/backup/`（pristine）、`_opt/final_src/`（本次最终版）。
* 本机没有 git，所以用目录快照做 A/B 重建（`_opt/backup` → 重建 → 跑 → 还原）。

## 5. 还没做的（留档，不是"判定不值得"）

* **head 反向的「按 token 批量」GEMM 化**：把 `dW[v][j] = Σ_t dY[v][t]·Ht[b(v)][j][t]` 在 token 维上
  归约，可把 `dw` 的 0.5 MB/Token 读写（现在是 128 次读改写同一块）降到一次读写。
  估算还能再快 3–8×（生产配置目前 head 只占 5%，所以端到端上限 ≈2–4%）。
* **attention 反向 passB/passC 的 GEMM 化**：现在每对 (i,j) 触碰 4 条 d 长向量，实测 ≈400 MB/region/步 的
  内存流量（带宽受限）；改成 t 维分块 GEMM 可把流量降一个数量级。生产配置里 attention 藏在
  「逐层反向 61.5%」内，这是剩下最大的一块。
* `tr()`（稠密路径转置）、`attn_qk_stats`（诊断）、生成路径的采样循环未动（不在训练热路径）。
* 用户允许的 **C 异构内核**未使用：本机 MSVC BuildTools 有 `cl.exe`
  （`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\cl.exe`），
  但实测下来的瓶颈是 **gather 吞吐 / store-port / L2 带宽**，Rust 的 `core::arch` 已经能发出同样的指令
  （`gather/ps`、`fmadd`、`maskload`），换 C 只会多一层 FFI；真正能突破的是算法结构（上面两条），
  不是语言。这条留作结论，不是"没条件做"。

## 6. 最终验证（收尾）

* 生产配置 30 步：**1.347 s/步（min 1.219）**，loss 9.01228 → **9.00578**（单调下降），
  `stopped_by=steps diverged=false`，exit 0。
* 全部 `_opt\log_*.txt`（约 30 次端到端运行）**扫描无 `NaN` / 无 `diverged=true` / 无 0xC0000005**。
* `vmlm-tests.exe`：**全部 PASS**；`vmlm-b1-verify` 20/20；`vmlm-b1-canfail` 7/7；
  `vmlm-b1-prod-eps` ALL PASS；`vmlm-bwd-check` PASS。
* 引擎体积：`target/release/vmlm-runtime.exe` = **74752 B（未变）**。
  注意：`cargo build --release --workspace` 会在 `vmlm-runtime` 的**链接步骤**报 LNK1561/1120 ——
  这是仓库自己在根 `Cargo.toml` 注释里写明的既有情况（no_std 引擎的 `/ENTRY` 等链接参数只在
  `runtime/.cargo/config.toml` 生效，工作区根构建读到的是根 config），与本次改动无关：
  该步之前 vmlm-core **编译通过**（报的是 linking 失败）。
