# P16-2: connection-sparse activation — `OP_TOPK_BY_STRENGTH` (93) + `OP_SPARSE_MATVEC` (94)

Generated by `tools/p16_sparse_ops.py`, `tools/p16_guardprobe.py` and
`tools/p16_asm_wiring.py`. Nothing here is hand-written; re-run those three to
regenerate.

## The two principles, and which opcode serves which

| principle | meaning | opcode |
|---|---|---|
| connection sparsity | each neuron keeps only its top-k connections (k0=20) | `OP_TOPK_BY_STRENGTH` = 93 |
| connection-sparse activation | **only surviving connections are computed** | `OP_SPARSE_MATVEC` = 94 |

They share one computed quantity: the connection activation strength
**s_i = w_i · x_i**.

## Encoding

```
TOPK_BY_STRENGTH  dst[L,2], strengths[L], k_scalar
    dst[:,0] = surviving connection index, ASCENDING
    dst[:,1] = that connection's strength
    rows nk..L are zero-filled

SPARSE_MATVEC     dst[n(+1)], offsets[n+1], src[nnz]
    w-slot  in ins.fl bits 0..5      x-slot in ins.dt
    fl bit6 = FL_NNZ  ->  dst[n] := multiply-adds ACTUALLY PERFORMED
```

## Results (all measured, see the three tools for raw output)

### Single-layer numeric proof — 6 inputs, 4 outputs, k0 = 2

```
CSR offsets = [0, 2, 4, 5, 7]      kept connections = 7
CSR src     = [0, 2, 1, 4, 2, 3, 5]  dense equivalent n^2 = 4 x 6 = 24
engine   y  = [0.14999985694885254, -2.700000047683716, 2.0999999046325684, -3.174999952316284]
Python   y  = [0.14999985694885254, -2.700000047683716, 2.0999999046325684, -3.174999952316284]
max|diff| = 0      -> BIT-EXACT (not merely close)
```

Bit-exactness is not luck: the surviving terms are summed in **ascending CSR
order**, which is the same order a dense product visits them.

### The skip proof

```
engine nnz (multiply-adds performed) = 7
kept connections                     = 7
dense equivalent n_neurons^2         = 24
skipped                              = 17  (70.8% of dense)
```

`s nnz` is written into `dst[n_neurons]` by the engine itself. It is a
*measurement*, not a printout: section E of the harness feeds a CSR that covers
every (j,i) pair and the same counter reports **24**, proving it counts the
traversal rather than echoing `len(src)`.

### Guards (every one shown FIRING, exit code 9)

| guard | message |
|---|---|
| k > L | `TOPK_BY_STRENGTH: k > L k=99 L=4` |
| k negative/NaN | `TOPK_BY_STRENGTH: k is negative or NaN` |
| src zero width | `TOPK_BY_STRENGTH: src or dst slot has width 0` |
| dst not [L,2] | `TOPK_BY_STRENGTH: dst must be [L,2] src=4x1 dst=4x1` |
| dst rows < L | `TOPK_BY_STRENGTH: dst needs L rows; L=4 dst=2x2` |
| src_id out of range | `SPARSE_MATVEC: src_id out of range t=2 src=9 nx=4` |
| offsets walk past src | `SPARSE_MATVEC: offsets out of range j=3 o0=3 o1=99 nnz=4` |
| offsets/src zero width | `SPARSE_MATVEC: offsets or src slot has width 0` |
| x (dt) zero width | `SPARSE_MATVEC: x slot (dt) has width 0` |
| dst too small for n | `SPARSE_MATVEC: dst must be [n_neurons(,1)] n=4 dst=2x1` |
| nnz needs one more cell | `SPARSE_MATVEC: nnz needs dst to be [n_neurons+1] 4x1` |
| offsets not n+1 long | `SPARSE_MATVEC: offsets must have n_neurons+1 entries` |

Assembler-side hard failures (panic, exit 3221226505, **no `.vmb` produced**):
weight slot number > 63 (does not fit `fl` bits 0..5); missing `x` operand.

## Two bugs this work found by measurement, not by review

1. **`TOPK_BY_STRENGTH` emitted in strength order, not index order.**
   `format.rs` promised ascending indices; the loop naturally produced
   descending-strength. Caught by control D4 (`indices=[4, 0] ascending=False`).
   Fixed with an insertion sort, because ascending order is what makes the
   output usable as a CSR *and* what makes the matvec bit-exact.

2. **Stack overflow to `0xC0000005`, no diagnostic.** The first version used
   `[usize; 4096]` buffers (~33 KB frame). The engine ships a *deliberate*
   no-op `__chkstk` stub (to avoid the CRT), so a frame that large skips the
   guard page. Measured `exit=3221225477` with empty stdout. Bounded by
   `TOPK_MAX_L = 2048` (18 KB) plus an explicit `exit(9)` above it.

## A design fact worth stating plainly

`OP_SPARSE_MATVEC` reads the **CSR**, not `OP_TOPK_BY_STRENGTH`'s output slot.
Changing `k` alone changes only the contents of `sel` and has **zero** effect on
`y`. The two opcodes compose **through the CSR**; `sel` is what a host/tool uses
to *build or audit* that CSR. An earlier can-fail control asserted "wrong k must
change y" and failed — correctly, because the assertion was wrong about the
design. Both halves are tested separately (D3 for the CSR half, D4 for `sel`).

## Reproduce

```powershell
cd <repo>
python tools/p16_sparse_ops.py --exe <bench engine> --asm target/release/vmlm-asm.exe
python tools/p16_guardprobe.py --exe <bench engine> --asm target/release/vmlm-asm.exe
python tools/p16_asm_wiring.py --asm target/release/vmlm-asm.exe
```

`<bench engine>` is built from `runtime/` with `--features bench` (the default
build has no argv/dump path, so it cannot report slot contents):
`cargo build --release --target x86_64-pc-windows-msvc --features bench`.

Build the engine from `runtime/` — cargo only reads `runtime/.cargo/config.toml`
from the invocation directory upward, and the engine needs those no_std link
flags.
