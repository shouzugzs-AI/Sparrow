## The gap (found by task-8, confirmed by the Lead)

read the CSR and **never re-read `sel`**. So `y` was fully determined by the CSR
and changing `k` did nothing.

## Bit-exactness

Every k is **bit-exact** vs the independent Python reference (max|diff| = 0).

The summation order that makes this true: for each neuron, the selected
connections are summed in **ascending row-relative index**, which is the same
order the engine walks — the gated path iterates `sel` segments (emitted
ascending) and the ungated path walks the CSR row ascending. Identical order +
identical f32 rounding = identical bits.

## The design (A′) and why

A `selgate` bit (**`fl` bit7**, previously unused) switches opcode 94 into a mode
that consumes `sel`; the same bit on opcode 93 (`seg`) makes it run **per row**.

1. **No instruction widening, no new opcode number.** `fl` bits 0–5 hold the
   weight slot, bit6 is `FL_NNZ`, bit7 was free. Reusing opcode 94 cannot
   collide with anyone else's number allocation.
2. **The ungated path is unchanged** (control D4: on the NEW engine the ungated
   form still reproduces the dense reference bit-exactly with `nnz=24`).
3. **It uses `sel` at inference.** The brief's Design B prunes the CSR at build
   time, leaving `k` as an assembler argument the engine never sees.

### Why `seg` is required as well

Opcode 93 numbers its output `0..L-1` over the array it is *handed*; opcode 94
numbers connections `0..nnz-1` over the *whole CSR*. Those agree only for row 0.
The engine's own guard caught this on the first gated attempt:

```
SPARSE_MATVEC: sel index outside its CSR row   j=0 idx=8 row=[0,6)
```

In segmented mode `a` is `[n,m]` and each row's survivors are emitted
**row-relative**, so 94 reads `o0 + rel` and the two numberings agree by
construction.

### Gated operand map

```
a      offsets[n+1]     row spans
b      src[nnz]         source-neuron id per connection
b + 1  sel[n, 2k]       per-neuron TOP-K selection (adjacency convention)
fl     weights[nnz]
dt     x                input activation vector
```

Only four slot fields exist after `dst`, so `sel` is named by **convention as
`src + 1`** — the same pattern `LN_BWD` (gamma/dg/db) and `OUTER_BWD` (k/dk)
already use. As there, the convention is **validated, not trusted**: the
assembler hard-fails unless the slot passed as the 6th operand really is `src+1`.

## Guards — 21/21 fire, each with exit 9 and its own message

The 16 task-8 guards still fire unchanged. Five new ones (task-11):

| guard | message |
|---|---|
| odd `sel` width | `SPARSE_MATVEC: selgate needs an even sel width sel=4x7` |
| `sel` rows < n | `SPARSE_MATVEC: sel table too small for n_neurons 2x8 n=4` |
| k > segment width | `TOPK_BY_STRENGTH: k > dst segment width k=2 seg=1` |
| seg rows != src rows | `TOPK_BY_STRENGTH: segmented dst rows != src rows src=4 dst=3` |
| **sel index outside its CSR row** | `... j=0 rel=1 row=[0,1)` |

The last one is the composition guard: a `sel` disagreeing with its CSR must be
**rejected, not summed** — summing it would read a weight belonging to another
neuron, i.e. a number that looks exactly like a real activation.
